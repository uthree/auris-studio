# 制作フェーズ

[English](composition-workflows.md)

ライブエージェントとワークショップの composer は、作曲・編曲・MIX の三つのフェーズに分けて曲を作ります。ツールカタログはどのフェーズでも全部見せます。別のフェーズが担当するものが必要になったとき、モデルがそれを見て前のフェーズに戻れるようにするためです。候補ツールを案内するには `AURIS_COMPOSITION_CANDIDATES=1` を設定します。評価ランナーはこのフラグを有効にします。既定のアプリケーションカタログを試すときは `--no-candidate-tools` を使います。ローカルモデルのコンテキストは既定で64kで、`--context-tokens` で明示的に記録できます。実験で予算を増やしても、アプリケーションの既定値は変わりません。

新しいボーカル曲で指定がなければ、第2ヴァースと後半のコーラス／エンディングを含めます。短い形式を明示した場合や局所編集では、その範囲を保ちます。セクションの網羅とスコアの読み戻しについては、[ライブボーカル制作](agent-workflows.ja.md#live-vocal-production)を参照してください。

`production_record` は `enter_phase` を受け取ります。引数は `phase`（`score`、`arrangement`、`mix`）と `reason` で、作曲フェーズでは `writing_order`（`harmony_first`、`melody_first`、`rhythm_first`）も指定できます。作曲フェーズでは形式、テンポ、コード、歌詞、主旋律とその歌声を決め、簡単なガイド伴奏つきのデモで終えます。編曲フェーズでは、固定された楽譜のまわりに音色、伴奏、ドラム、演奏表現、転換を作ります。MIX フェーズでは、バランスを取り、エフェクトをかけ、納品します。`set_roles` で主旋律のトラックとガイドのトラック（または理由つきの `no_foreground`）を登録します。編曲に入るには、この登録が必要です。部分的な修正は、直す対象を担当するフェーズに入って行います。

フェーズは会話メタデータであり、他の記録更新と同じ書き込み権限の対象です。コンテキスト圧縮や会話の再起動後も保持されます。システムプロンプトは共通の核だけです。共通の核は、どのフェーズでも成り立つ規則（ID・revision・単位、失敗からの回復、範囲の守り方、正直さ）をまとめたものです。各フェーズの指示、ツールの要点、定石の索引は、フェーズに入ったときと記録を読んだときに `phase_instructions` として返ります。記録が長いと `read_report` のページに分けられますが、指示はページの中ではなく記録の横に付きます。それ以外の記録の更新とプロジェクトの検査には付きません。定石の索引は [composition techniques](composition-techniques.md) の見出しを挙げたもので、`search_documentation` で引けます。曲のジャンルと用途を決めると（`edit_timeline` の `set_style`。文書に保存されます）、指示の最後に `docs/genres/` と `docs/usages/` の該当ページが付きます。付くのはページの要約と、いまのフェーズの節です。判定もスタイルに従います（対応表は `auris_session::session::style_checks`）。ループ BGM と劇伴キューにはイントロとアウトロを求めません。音域を上げるサビがないジャンル（ジャズ、オーケストラ、アンビエント、ヒップホップとローファイ、ダンス）にはサビで上げることを求めません。ループで作るジャンルでは、サビが A メロと同じ進行でも構いません。ジャズ、R&B、シティポップ、ラテンでは、キー外の音を伸ばしても警告ではなく情報として報告します。前のフェーズに戻っても後ろのフェーズの成果は残り、`phase.revisit` にやり直すフェーズが並びます。`phase.checks` は、現在とそれ以前のフェーズについて満たされていない構造上の条件を、`inspect_project` の `phase_facts` から読んで報告します。作曲では曲全体を覆うセクション、全セクションのコード、役割の登録、歌詞注記、最新の歌声テイク、編曲ではドラムの割り当てとガイドの置き換え、MIX では全体ミックスの測定です。これらは警告で、拒否ではありません。

フェーズが固定するものは、プロンプトではなくホストが守ります。編曲フェーズでは主旋律のトラックのノートと歌詞、コード、セクション、拍子、テンポマップが固定され、MIX フェーズではさらにすべてのノート、音色、演奏表現が固定されます。ホストはエージェントの編集ごとに、固定された素材をタイムライン上で鳴る位置で前後比較し、変えてしまった編集を取り消します。文書と Undo の履歴は元のまま残り、モデルには何が変わったかと、変えるにはどのフェーズに入ればよいかが返ります。時間のかかるジョブは、結果を文書に書き込む時点で比べます。作曲に戻ってから再び進むと、変わった小節とそこで鳴るトラックが `phase.review` に並ぶので、編曲はまずそこを直せます。

ワークショップはラウンドで進みます。新しい曲では、ディレクターがまずデモを2〜3本出します（`"phase": "score"`）。デモは役割を登録した作曲の段階で止まり、候補カードに「デモ」と表示されます。ユーザーが一本を選ぶと、`"phase": "finish"` の assignment がそれを引き継いで編曲フェーズに入り、メロ・歌詞・コードを固定したまま MIX まで仕上げます。各候補は曲の横に制作記録を残すので、仕上げはデモの役割から始まります。

Linter の warning と error は、プロンプトの指示だけに任せず、ホストが知らせます。`inspect_project` は毎回その件数を `phase_facts.lint` に数え、作曲フェーズのチェックは `lint_warnings_resolved` として並べます。このチェックは後のフェーズでも読まれます。ワークショップの composer が warning を残したまま候補を完成と報告すると、ホストは先頭の指摘を付けて、2回まで差し戻します。それでも残ったものは `composer-log.jsonl` に記録し、候補はそのまま残します。早く終えるモデルは lint の指示を読み飛ばしますが、差し戻しの返事は読み飛ばせません。
早く終えるモデルは lint の指示を読み飛ばしますが、差し戻しの返事は読み飛ばせません。

途中で止まった曲も、同じ差し戻しで戻します。ホストは今のセッションを読み、制作記録が到達したフェーズのうち満たしていない構造チェックを並べます。並べるのは、セクションとコードが曲を覆っているか、役割、歌詞、歌のテイクが最新か、ドラム、仮の伴奏を置き換えたか、主旋律が曲の小節の半分以上で鳴っているか（`phase_facts.tracks[].bars_with_notes`）です。デモ以外の候補は、MIX フェーズまで進んでいる必要もあります。測定の範囲は除きます。編集のたびに古くなるからです。フェーズに一度も入っていない記録も対象外です。

共通契約は、正確なID、ティック単位、リビジョン検査、ソース保持、探索上限、測定値・批評家レポート・人間の聴取の区別を維持します。ワークフロー指示はモデル向けの案内であり、正規のセッションコマンドが検証と権限を個別に強制します。保留中の候補判断は、その有効期間内ならターンをまたいでラウンドとIDを保持します。ターンの終了だけを理由にラウンドをキャンセルしないでください。

制御された比較では、同じ固定実行ファイル、モデル、タスク群、ツールカタログを使い、`composition_quality.py run` を実行します。バックエンドのトークンカウンターとともに失敗と経過時間を記録してください。最後に報告された入力コンテキストは累積課金入力ではないため、利用量が欠落している場合にゼロコストとして扱ってはいけません。
