# 認識器に依存しない採譜 API

[English](transcription-api.md)

ライブエージェントはローカルツールで添付音声を解析し、外部の解析ツールで用意したノート下書きをインポートできます。同じ契約を Codex、Claude Code、ネイティブ API の各トランスポートで利用できます。トランスポートからローカル解析ツールへアクセスできる必要があります。ファイルを書き出しただけで、モデルが音声を聴いたり認識器を提供したりするわけではありません。

<a id="export-the-attached-source"></a>
## 添付ソースを書き出す

ホストの音声メタデータにある `attachment_id` を `attachment` に設定して `export_audio_attachment` を呼び出します。結果には `audio_path`、`sha256`、`bytes` が含まれます。パスは絶対パスで、リサンプリングやチャンネル変換をしていない元バイト列の完全なコピーです。ファイル名、テンポ、コードの概要はスコアではありません。

コピーはホストの元スナップショットとは別です。変更しないでください。添付ごとに現在の書き出しは1つだけで、次の書き出しが前のファイルを置き換えます。添付の追い出しや会話の終了でもコピーは削除されます。長く保持するには解析用ワークスペースへコピーしてください。元ファイルには1ファイル512 MiB、会話1 GiB、添付8個という既存の上限があります。保持した書き出しには最大でさらに1 GiBと、最大512 MiBの処理中コピー1つが加わります。コピーとハッシュ計算は、WAV全体を RAM に読み込まず、キャンセル可能なチャンクでストリーム処理します。この操作は `export_audio_attachment` の権限規則に従い、ドキュメントを編集・保存しません。

<a id="import-a-note-draft"></a>
## ノート下書きをインポートする

`import_transcription` には 外部ピアノオブジェクト（下記）の `transcription`、そのオブジェクトを含む絶対パスのローカル JSON ファイル `path` のいずれか1つだけを指定します。任意の `name` の既定値は `Transcription`、`at_tick` は0以上の絶対挿入ティックで既定値は0です。大量のイベントは、チャットに何千件も置かず JSON ファイルを使ってください。

```json
{
  "source": {
    "method": "codex.harmonic-fit",
    "model": "gpt-6.1-sol"
  },
  "seconds": 2.0,
  "notes": [
    {"pitch": 60, "start": 0.25, "end": 1.5, "strength": 0.65},
    {"pitch": 64, "start": 0.25, "end": 1.5, "strength": 0.65}
  ],
  "limitations": "Uniform dynamics; review missed notes and offsets."
}
```

`source.method` は必須（1〜128バイト）です。任意の `model` は空でない最大256バイトの名前です。任意の `artifact_sha256` は実際に使ったモデルまたは解析プログラムを、`audio_sha256` は解析した元バイト列を識別します。各ハッシュは64個の16進文字でなければなりません。これらは呼び出し側の主張であり、ホストは認識器を認証せず、音声との対応を確認せず、音楽的な正確さを証明しません。受理されても認識精度は保証されません。来歴と制限は呼び出し元に返され、スコアには保存されません。再現可能な解析が必要なら元 JSON とハッシュを保持してください。

長さとイベント時刻は有限値で、`0 < seconds <= 600`、`0 <= start < end <= seconds` を満たす必要があります。ノートは1〜200000件、MIDIピッチは21〜108、`strength` は有限の0〜1を明示します。重なりは保持してください。汎用インポートは0.1未満を含め、指定された強度を保持します。ダイナミクスがない場合は、選んだ一様値を `limitations`（最大4096バイト）に書きます。不正な下書き、未知のトップレベル／source フィールド、強度の欠落は編集前に失敗します。ファイルは最大32 MiBの通常のローカルファイルで、相対パスと UNC／デバイスパスは拒否されます。読み込みはキャンセルできます。

ファイル読み込みはまず `cli_file_read` 権限ゲートを通り、検証済み下書きは対象のコマンドとドキュメントリビジョンに結び付いた承認で `edit_project.import_transcription` を通ります。Read-only と Plan モードでは編集を拒否します。受理すると物理ピアノのトラックとクリップを1つ追加し、既存の音楽、テンポ、ソースの演奏タイミングをプロジェクトのティック解像度で保持します。1回の Undo で、区間が0ティックに潰れるノートが1つでもあれば下書き全体を拒否するため、短いノートが黙って消えることはありません。変更は未保存のままです。結果の確認には `read_notes` と `inspect_audio` を使います。

保存済みプロジェクトの MCP では同じインポート契約に必須の `project` が加わり、変更結果をチェックポイント付きで保存します。ライブのインポートは未保存です。

<a id="validation"></a>
## 検証

2026-10-21、Codex 主導の採譜実験で凍結した129ノートの混合下書きを、保存済み MCP の `import_transcription` でインポートし、チェックポイントを作成して物理ピアノでレンダリングしました。129音すべてが残り、100 BPM、1拍960ティックでの開始／終了変換誤差の最大値は0.31 msでした。一様強度0.65も明示しました。48 kHz ステレオ float32 の WAV はエンコード検査に合格し（38.39秒、ピーク -11.0 dBFS、フルスケールサンプルなし）、SHA-256 は `86f8d72439db88eefeeb0a2e6583ba386da66cff24c34ea1822fbbb41c5f5675` でした。これは既存の推定を再利用して API 統合を検証したもので、認識品質の検証ではありません。

続く実アプリでの評価では、元音声の書き出し、独立解析、汎用インポート、レンダリング結果の確認、Undo／Redo を実際のモデル推論で実行し、2つの凍結 DSP 手法を Basic Pitch と比較します。
