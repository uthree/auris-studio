### F-077 · high · Automation writes to a hosted CLAP effect's parameter can change its reported latency without ever marking `latency_stale`, unlike the discrete SetEffectParam command path.

`crates/auris-engine/src/device.rs:800` · spec-mismatch · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** When an automation lane drives a hosted CLAP effect's parameter that changes the plugin's own reported latency, the delay-compensation lines silently fall out of sync with the graph's actual latency, but `EngineHandle::latency_is_stale()` keeps reporting false. The UI never surfaces the mismatch, so tracks can drift out of phase/sync during automated playback with no warning, and nothing prompts the user (or any caller) to rebuild/republish latency.

**Trigger.** A track chain contains an effect whose latency_frames() depends on a parameter under automation — graph/mod.rs's own doc at latency_is_stale() names the shipped example: "the limiter's lookahead is the only one that ships." As playback runs and the automation lane moves that parameter (drive_automation runs every block via apply_automation), the effect's real latency changes each time RenderGraph::latency_is_stale() would detect a mismatch against `built_latencies`, but nothing on the audio thread ever calls it again after the graph was built or after the last discrete SetEffectParam command.

**Mechanism.** AudioEngine::publish_latency() (device.rs:604-610) — the sole caller of RenderGraph::latency_is_stale() in the engine (confirmed by `grep -rn latency_is_stale`, its only callers are device.rs:608 and a graph/latency.rs test) — is invoked from exactly two places inside AudioEngine::apply(): the EngineCommand::SetGraph arm (line 727) and the EngineCommand::SetEffectParam arm (lines 789-801, whose own comment at 798-799 reads "this is the one command that can leave the delay lines compensating for the wrong number of frames"). AudioEngine::fill() (lines 612-662), the per-callback render path, never calls publish_latency() unconditionally. But effect parameters are also written on the audio thread by automation: renderer.rs:91 calls graph.apply_automation() unconditionally every block, which calls drive_automation() (graph/automation.rs:123-183); its AutomationSlot::Effect arm (automation.rs:173-180) calls `track.strip.set_effect_param(...)` / `master.set_effect_param(...)` directly, the same setter SetEffectParam uses (per automation.rs's own doc: "there is no second path into a […]

**Expected.** Three separate doc comments describe the intended invariant and all three are broader than what device.rs implements: device.rs:555-557 ("nothing but writing an effect parameter can move it"), graph/mod.rs:782 ("the audio thread asks it once per callback"), and handle.rs:172 ("The audio thread re-checks after each such write"). All three frame this as covering every write to an effect parameter, not just ones that arrive as a discrete EngineCommand::SetEffectParam; automation writes the […]

**Fix direction.** Make `latency_stale` reflect reality regardless of which thread wrote the parameter: either have `drive_automation`'s `AutomationSlot::Effect` arm also recompute/publish latency staleness (cheaply, without allocating, e.g. by comparing a cached compensation total to the graph's current latency total on the RT thread using the existing atomic), or have `render_segment`/`fill()` call `publish_latency()`-equivalent logic once per callback so any effect-parameter path (command-driven or automation-driven) keeps the flag correct.

**Written rule it breaks.** // A look-ahead length is a parameter like any other, so this is the one command that can leave the delay lines compensating for the wrong number of frames. (device.rs, EngineCommand::SetEffectParam handling, documenting the very invariant that automation silently breaks)

### F-088 · high · Soloing a track during playback rebuilds the graph and settles MuteFade instead of sliding it, producing an audible click, contradicting strip.rs:251's own doc comment.

`crates/auris-engine/src/graph/strip.rs:278` · spec-mismatch · confirmed (traced through the code; reported independently 1×)

**What a user sees.** Clicking Solo (or un-soloing) on a track while the transport is playing produces an audible pop/click on every track whose audibility changes, because the graph swap that solo triggers replaces the live RenderStrip with a freshly constructed one whose MuteFade is built already settled (RenderStrip::new / MuteFade::new at strip.rs:278) rather than reached through the sliding set_audible path — the exact same-sample level jump the MuteFade mechanism exists to prevent for mute.

**Trigger.** While the transport is playing (or a live monitor/record pass is running), the user clicks Solo (or un-solos) on any track. The very next audio callback swaps in the freshly rebuilt graph.

**Mechanism.** `RenderStrip::fade`'s own doc comment (strip.rs:251) states: "Mute and solo as a gain, so switching either one slides instead of stepping." But `audible` (which carries the solo resolution) is only ever set at construction time — `RenderStrip::new` (strip.rs:270-283) always builds the fade already **settled**: `fade: MuteFade::new(audible && !mute, sample_rate)` (line 278), which per `MuteFade::new`'s own doc "puts the fade where it would have ended up, with nothing left to slide." The only method that actually *slides* a change in audibility on a live strip is `RenderStrip::set_audible` (strip.rs:415-418, `fade.set_open(...)`), reached only through `RenderGraph::set_audible` (graph/mod.rs:840-844). But solo has no `EngineCommand` variant at all (command.rs's `EngineCommand` enum has `SetTrackMute` but no `SetTrackSolo`), and `Session::set_track_solo` (auris-session/src/session/tracks.rs:295-303) says so explicitly: "unlike mute it cannot be expressed as one per-track command and the graph is rebuilt instead" — it only flips `track.mixer.solo` and calls `self.invalidate_graph()`. […]

**Expected.** Per strip.rs:251 ("switching either one slides instead of stepping") and the whole rationale of `MuteFade`, a solo toggle during playback should cross the same ~5 ms slide a live mute gets. Either solo needs its own live `EngineCommand` (as mute has) instead of a full rebuild, or the rebuilt graph needs to inherit the outgoing graph's in-flight `MuteFade`/`audible` state instead of starting settled.

**Fix direction.** Give solo a live per-track EngineCommand (mirroring SetTrackMute) that calls RenderGraph::set_audible on the existing playing graph instead of forcing Session::set_track_solo to invalidate_graph/rebuild; alternatively, when a rebuild does occur during playback, have the new graph inherit each strip's outgoing in-flight MuteFade/audible state instead of constructing it settled.

**Written rule it breaks.** /// Mute and solo as a gain, so switching either one slides instead of stepping. (crates/auris-engine/src/graph/strip.rs:251, doc comment on RenderStrip::fade)

### F-089 · high · Input stream setup lacks output's Fixed-buffer-size retry fallback, so WASAPI-class devices fail to open for recording instead of falling back like output does.

`crates/auris-engine/src/capture.rs:702` · spec-mismatch · confirmed (traced through the code; reported independently 1×)

**What a user sees.** On a backend that refuses an explicit buffer size (WASAPI in particular, per the existing comment in device.rs), opening the recording/input stream with a preferred block size fails outright and recording cannot start — where the identical situation on the output side is silently absorbed by falling back to the device's own buffer size. The user sees an error trying to record instead of audio just working at whatever buffer size the device offers.

**Trigger.** `start_capture(&CaptureSettings { block_frames: Some(frames), .. }, engine)` on an input device where `frames` is rejected by the OS layer for an explicit buffer size — the same backend behavior (WASAPI refusing a fixed size) that device.rs's own commit history ("Several backends (WASAPI in particular) refuse an explicit buffer size outright") establishes as a real, observed occurrence, and which applies equally to `build_input_stream` since cpal's WASAPI implementation resolves `BufferSize::Fixed` into the same `IAudioClient::Initialize` buffer-duration path for both directions.

**Mechanism.** `CaptureSettings::block_frames`'s doc comment (capture.rs:152-153) reads "Preferred callback size in frames. Ignored when the device cannot do it." — identical wording to `AudioSettings::block_frames` in device.rs. For output, that promise is actually kept: `start_with_device` (device.rs:268-292) tries `build_stream` with the requested `BufferSize::Fixed`, and on failure explicitly retries with `BufferSize::Default` ("Several backends (WASAPI in particular) refuse an explicit buffer size outright. Losing all audio over a *preference* would be much worse than ignoring it, so retry with whatever the device wants"). `open_input`/`start_capture` build the identical `BufferSize::Fixed(frames)` (capture.rs:779-793) but `start_capture`'s stream construction (capture.rs:702-708) has no such retry: `input_stream::<T>(...)` is called once and its `Result` is propagated straight up with `?` (line 707). Any error from `build_input_stream` — including exactly the "backend refuses an explicit buffer size" case the sibling file's own comment names — makes `start_capture` return `Err`, which […]

**Expected.** `start_capture` should retry `input_stream` with `BufferSize::Default` on a rejected `Fixed` size, mirroring `start_with_device`'s retry (device.rs:279-292), so the documented "ignored when the device cannot do it" behavior actually holds for the input device the way it already does for the output device.

**Fix direction.** In capture.rs's stream-opening path (where `open_input`'s `InputSetup` is turned into a running stream, mirroring `start_with_device` in device.rs:267-292), catch a build failure when `config.buffer_size` is `BufferSize::Fixed(_)`, log a warning, set it to `BufferSize::Default`, and retry once before propagating the error — the same pattern already implemented for output.

**Written rule it breaks.** "Preferred callback size in frames. Ignored when the device cannot do it." (identical doc comment on both device.rs:38 and capture.rs:151)

### F-096 · high · Windows output devices whose default WASAPI mix format is I24/I32/I64/F64/U8 (e.g. a common "24-bit" device default) silently fall back to a fully silent audio engine with no error dialog, only a log warning.

`crates/auris-engine/src/device.rs:516` · platform · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** On a Windows machine whose default output device's WASAPI shared-mode mix format is not 16-bit int or 32-bit float — e.g. a device set to "24-bit, 48000 Hz" in the Sound Control Panel, which is a common out-of-the-box default for many onboard/Realtek and audio-interface drivers — `open_output` reads that mix format via `device.default_output_config()` and passes it to `build_stream`, whose match only handles F32/I16/U16. Every other cpal `SampleFormat` (I24, I32, I64, F64, U8) hits the `other => Err(EngineError::UnsupportedSampleFormat(...))` arm. `start_audio` catches that error and silently falls back to `start_silent`, logging only a `log::warn!` line. The application launches normally, the transport appears to run, but no audio ever reaches the speakers, and there is no dialog or visible indication — the user just hears nothing and has to find the warning in a log file to learn why.

**Trigger.** Any Windows machine whose output device's Sound Control Panel "Default Format" is set to something other than 16-bit or 32-bit float — e.g. the common "24 bit, 48000 Hz (Studio Quality)" preset many Realtek/onboard and audio-interface drivers ship with, or ship with as their out-of-the-box default. `cpal::default_output_config()` then reports `SampleFormat::I24`.

**Mechanism.** `open_output` (line 398-399) picks `sample_format` from `device.default_output_config()` — on cpal's WASAPI backend that is whatever `IAudioClient::GetMixFormat` reports for the device's *current* shared-mode format, which cpal maps (see `~/.cargo/registry/src/.../cpal-0.18.1/src/host/wasapi/device.rs:229-251`) to `U8`, `I16`, `I24`, `I32`, `I64`, `F32` or `F64` depending on the bit depth and format tag actually configured for the device. `build_stream` (lines 496-517) only has match arms for `SampleFormat::F32`, `SampleFormat::I16` and `SampleFormat::U16`; every other value — `I24`, `I32`, `I64`, `F64`, `U8` — falls into `other => return Err(EngineError::UnsupportedSampleFormat(...))`. `start_audio` (lines 217-231) catches that `Err` from `start_with_device` and quietly falls back to `start_silent`, logging only a warning.

**Expected.** The device-open path should either request/negotiate an `F32` configuration explicitly (WASAPI shared mode accepts a client-requested format that differs from the mix format, via format conversion) or handle the remaining `cpal::SampleFormat` variants (`I24`, `I32`, `I64`, `F64`, `U8`) the way `I16`/`U16` are already handled, rather than treating them as fatal and dropping to a fully silent engine.

**Fix direction.** Either request an explicit F32 stream configuration from WASAPI shared mode (cpal/WASAPI will do the sample-format conversion) instead of taking whatever `default_output_config()` reports, or extend `build_stream`'s match to cover the remaining `cpal::SampleFormat` variants (I24, I32, I64, F64, U8) the same way I16/U16 are already handled by converting into the engine's internal sample representation. Either change removes the case where a common, unremarkable device setting silently degrades a Windows install to no audio.

**Written rule it breaks.** CLAUDE.md: "Development happens on macOS, so the Windows-only paths are the ones that rot" — the rules that follow exist specifically to keep Windows paths from silently breaking, and this is exactly such a silent Windows-only breakage that no test or CI check on macOS would ever surface.

### F-197 · medium · chase_notes re-triggers all overlapping same-pitch voices at the last note's velocity, losing each note's own dynamics on seek/loop/resume.

`crates/auris-engine/src/renderer.rs:457` · correctness · confirmed (executed reproduction; reported independently 1×)
