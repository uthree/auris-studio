### ✅ F-026 · critical · Session's field order drops the retired-graph channel before the live cpal stream, letting the audio callback free a RenderGraph on the realtime thread during shutdown.

`crates/auris-session/src/session/mod.rs:269` · realtime · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** When Auris Studio quits (or a project's Session is dropped) shortly after any structural edit — which sends a SetGraph command as part of essentially every edit — a retired RenderGraph (holding plugin instances and sample buffers) can be freed by a heap deallocation running inside the live cpal audio callback, in the window between the command/garbage channel being torn down (engine field drops first) and the output stream actually being stopped (device field drops second). That is exactly the allocator-on-the-audio-thread situation the Retired/garbage-collection channel exists to prevent, and it can produce an audible click/xrun in the last buffers played before the app closes, or stall the callback.

**Trigger.** Any edit that queues a graph rebuild — which is virtually every structural edit, since `rebuild_graph` (mod.rs:1017-1034) sends `SetGraph` on every one — immediately followed by quitting the application or closing the window (`AurisApp::on_quit` in crates/auris-gpui/src/ui/root.rs:1574-1582 just calls `cx.quit()` with no explicit `device.pause()`/stop first). The audio callback runs continuously (every ~10 ms) regardless of transport state, so the command frequently has not yet been drained when `Session` — and its `engine`/`device` fields — are dropped in the same synchronous cascade.

**Mechanism.** `Session` declares `engine: EngineHandle` at line 269 and `device: Option<AudioDevice>` at line 270 (crates/auris-session/src/session/mod.rs:269-270). Rust drops a struct's fields in declaration order after its own `Drop::drop` runs, so when `Session` is dropped (`impl Drop for Session` at mod.rs:1109, which only calls `self.abandon_take()` at 1119 — nothing about the output stream), `engine` — and with it `EngineHandle::returned_graphs: Receiver<Retired>` and `EngineHandle::commands: Sender<EngineCommand>` (crates/auris-engine/src/handle.rs:35-36) — is dropped strictly before `device`, which owns the actual `cpal::Stream` (crates/auris-engine/src/device.rs:119, `stream: Option<cpal::Stream>`) still driving the OS audio-callback thread. Between those two field drops the audio callback (`AudioEngine::fill` -> `poll_commands` -> `apply`/`flush_retired`/`retire`, device.rs:613-865) can still run on its own OS thread, because nothing pauses or joins the stream first. If a `SetGraph`/`PlayOneShot` command is still sitting in the (now-Sender-dropped-but-not-yet-empty) bounded `commands` […]

**Expected.** The output stream must be stopped (or at minimum the callback guaranteed not to run) before `EngineHandle`'s command sender and retired-graph receiver are torn down — e.g. by declaring `device` before `engine` in `Session` (so it drops first) or by explicitly pausing/dropping the stream in `Session::drop`/`abandon_take` ahead of the automatic field drops, consistent with the project's own realtime contract in CLAUDE.md and the doc comments on `Retired` and `flush_retired`.

**Fix direction.** Reorder Session's fields so `device` is declared (and thus dropped) before `engine`, or have `Session::drop`/`abandon_take` explicitly stop the cpal stream before the engine's command sender and `returned_graphs` receiver are torn down, so the audio callback can no longer run once the retired-graph channel disconnects.

**Written rule it breaks.** No allocation, locking, blocking or I/O in those paths. (CLAUDE.md, "Realtime rules")
