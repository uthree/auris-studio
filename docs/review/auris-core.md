### ✅ F-014 · critical · CurvePoint lacks the finite-value guard AutomationLane and set_param already enforce, so a NaN bend/controller value round-trips to JSON `null` and makes the whole project file unreadable.

`crates/auris-core/src/project/curve.rs:28` · persistence · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** A NaN pitch-bend or controller value (reachable via clamp(NaN,..)=NaN, e.g. from a UI drag computation or plugin-driven automation feeding set_curve_point/move_curve_point) gets stored in the clip's curve. On save, serde_json writes that f32 as JSON `null`; on the next load, deserializing the MidiClip fails outright with "invalid type: null, expected f32" — the entire project file becomes unopenable, not just the one clip.

**Trigger.** Either (a) a hand-edited or corrupted `.auris` file containing `"bend":[{"at":0,"value":1e40}]` — a syntactically ordinary JSON number that overflows `f32` to `Infinity` on the cast serde_json performs for f32 fields — loads without error via `load_project`; or (b) any caller of `Session::set_curve_point`/`move_curve_point` with `value = f32::NAN` (reachable from a UI computation bug, a scripted client, or a future toolbox exposure) stores the NaN untouched because `clamp` does not sanitise it.

**Mechanism.** `CurvePoint` (`pub struct CurvePoint { pub at: Ticks, pub value: f32 }`, curve.rs:28-33) derives plain `Serialize`/`Deserialize` with no `#[serde(try_from = ...)]` validator, unlike every other timeline map in this crate: `AutomationLane` (automation.rs:61-105) routes through `AutomationLaneRepr` and rejects any point where `!point.value.is_finite()`; `TempoMap` (time.rs:706-765) does the same for `bpm`; `SignatureMap` (time.rs:422-474) normalises a degenerate signature through `TimeSignature::new`. `CurvePoint` (stored in `MidiClip::bend` and `MidiClip::controllers`, project/clip.rs:190/202) has no such gate, so a `value` of `Infinity`/`NaN` deserialises without error. The session-layer writers mirror the gap: `Session::set_curve_point` and `Session::move_curve_point` (crates/auris-session/src/session/clips.rs:42-70 and 79-108) do `let value = value.clamp(low, high);` (lines 51 and 88) and nothing else — `f32::clamp` passes a NaN `self` straight through unmodified, so a NaN argument is stored verbatim. This is precisely the failure mode the same crate already named and fixed twice […]

**Expected.** Per the project's own stated and enforced rule (mixer.rs:345-351, tracks.rs:537-547, automation.rs's `AutomationLane` validation), any f32/f64 written into a document field must be checked with `is_finite()` before it is stored, and no such value should be accepted silently from disk either. `CurvePoint` should carry the same `#[serde(try_from = ...)]` guard `AutomationLane` and `TempoMap` do, and `Session::set_curve_point`/`move_curve_point` should reject or floor a non-finite `value` the way […]

**Fix direction.** Give CurvePoint (or MidiClip's bend/controllers) the same guard the crate already uses elsewhere: route deserialization through a `#[serde(try_from = "...")]` repr that rejects non-finite values, mirroring AutomationLaneRepr::try_from in crates/auris-core/src/automation.rs; additionally make Session::set_curve_point/move_curve_point reject or sanitize non-finite input before clamp (clamp itself passes NaN through unchanged), matching Session::set_param's explicit `is_finite()` check.

**Written rule it breaks.** AutomationLane doc comment: "Invariants, upheld by every constructor and mutator: ... every value finite." / Session::set_param comment: "A value that is not a number is not stored: NaN slips every clamp downstream, and `serde_json` writes a non-finite float as `null`"

### ✅ F-019 · critical · repair_id_counter's unchecked `highest + 1` panics (debug) or silently wraps to 0 (release) on a u64::MAX id in a loaded project file.

`crates/auris-core/src/project/mod.rs:579` · persistence · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** Opening a project file whose JSON contains a corrupted or maliciously crafted id of u64::MAX crashes the DAW immediately in a debug build (panic: "attempt to add with overflow" at repair_id_counter, mod.rs:579), and in a release build silently wraps next_id to 0, so ids handed out afterward can collide with existing tracks/clips/effects — corrupting the project's identity space without any error shown to the user.

**Trigger.** Open a `.auris` project whose JSON contains an id at the u64 boundary, e.g. `"tracks":[{"id":18446744073709551615, ...}]` (or the same value in any effect-slot id, send id, clip id, audio-source key, soundfont key, or directly as `"next_id":18446744073709551615`). `auris_io::project_file::load_project` (crates/auris-io/src/project_file.rs:194) parses the document with `serde_json::from_str` and immediately calls `project.repair_id_counter()` before anything else touches it — no upstream validation exists to catch the value first.

**Mechanism.** Every id type stored in the document (TrackId, ClipId, EffectSlotId, SendId, SourceId, SoundFontId — all `pub struct Foo(pub u64)` with `#[serde(transparent)]`) is deserialized straight from a JSON number with no range validation, and the private `next_id: u64` counter (line 289) is likewise deserialized from the document verbatim with no clamp or custom Deserialize impl. `repair_id_counter` (lines 551-580) folds every id it finds into `highest` via `u64::max` and then unconditionally computes `self.next_id = self.next_id.max(highest + 1)` (line 579) using the plain `+` operator, which is overflow-checked in the project's own dev profile (Cargo.toml sets `[profile.dev] opt-level = 1` but never disables overflow-checks, so the default debug_assertions-driven overflow checking stays on). If any single id anywhere in the document equals `u64::MAX` (18446744073709551615), `highest` becomes `u64::MAX` and `highest + 1` overflows. The same class of bug is reachable via `allocate_id` (line 461, `self.next_id += 1`) if the document's own `next_id` field is set at or near `u64::MAX`, since […]

**Expected.** The function's own doc comment (mod.rs:549-550) states its purpose is to make sure "the id counter is past every id in use, so ids handed out later cannot collide with existing ones" for exactly this reason — CLAUDE.md's project-folder section describes `repair_routing`/`repair_id_counter` as the designed answer to a file 'written by another tool or edited by hand'. A hostile or corrupted id should be absorbed (e.g. `self.next_id = self.next_id.max(highest.saturating_add(1))`) rather than crash […]

**Fix direction.** Replace the unchecked `self.next_id = self.next_id.max(highest + 1)` with `self.next_id = self.next_id.max(highest.saturating_add(1))` (or checked_add with a clamp to u64::MAX), and do the same for any other unchecked +1 on stored ids in this function; optionally validate/reject id values at deserialization time rather than trusting the file verbatim.

**Written rule it breaks.** Missing assets are reported, never fatal: the project opens with that one track silent. (project folder invariant — a malformed/corrupted file should degrade gracefully, not crash or silently corrupt state)

`crates/auris-core/src/time.rs:668` · correctness · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** A user who changes a project's opening time signature (via SignatureMap::set_initial, reachable from any UI/CLI edit of the initial meter) or simply loads a saved project file with three or more time-signature changes can silently lose one of their signature changes entirely — its meter value and position vanish with no error — while a later, unrelated signature change is silently relocated to a tick position over a bar away from where the user placed it. It does not anticipate or document a case where an unrelated, non-colliding point is swallowed purely because an *earlier* point's own bar-rounding overshot forward past it. ### ✅ F-003 · high · A saved audio clip with an out-of-range loop_end hangs graph build on project open, with no cap in loop_passes and no validation on deserialize.

`crates/auris-core/src/project/clip.rs:122` · persistence · confirmed (executed reproduction; reported independently 2×)

**What a user sees.** Opening a project whose file has an audio clip with an out-of-range `loop_end` (e.g. from disk corruption, a hand-edited or externally-generated `.auris` file, or a future format writing a larger value) freezes Auris Studio indefinitely while `resolve_audio_clip` builds the render graph: `loop_passes` iterates from pass 0 upward with `offset = pass * span`, and with `loop_end` near `i64::MAX` against a small `span` that loop runs on the order of `i64::MAX / span` times with no cap, so the UI thread never returns and the user must force-quit, taking any other unsaved work in the process with it.

**Trigger.** Open a `.auris` project (hand-edited or corrupted) containing an audio track whose clip has a short trim (e.g. `length_frames` corresponding to a handful of ticks) and `"loop_end": 9223372036854775807` (or any value many orders of magnitude larger than the clip's own length). No playback needed — merely opening the project triggers `Session::open` -> `rebuild_graph` -> `resolve_audio_clip` -> `loop_passes(...).collect()`.

**Mechanism.** `loop_passes(content, loop_end)` (clip.rs:122-129) iterates `pass * span` from 0 until `offset >= total`, where `total = loop_end.raw().max(span)`. `AudioClip::loop_end` (clip.rs, field around line 512) is a plain `Ticks(i64)` deserialized with only `#[serde(default)]` — no range or ratio validation against the clip's own length. `resolve_audio_clip` (crates/auris-engine/src/graph/schedule.rs:187-250) calls `loop_passes(content, clip.loop_end).collect::<Vec<_>>()` for every audio clip while building the render graph, where `content` is the clip's own (possibly very short) trimmed length in ticks. `resolve_audio_clip` is invoked from `RenderGraph::build`/`build_with` (crates/auris-engine/src/graph/mod.rs:386-403), which `Session::open` (crates/auris-session/src/session/files.rs:232-262) calls unconditionally via `self.rebuild_graph()` right after `load_project`.

**Expected.** Project loading should treat an implausible `loop_end` (or the resulting pass count) as a value to clamp or reject, the way the project explicitly guards other loaded fields (e.g. `AutomationLane::new` rejects non-finite/negative points, `MAX_DENOMINATOR_POWER` in the MIDI importer, the SoundFont chunk-size walk in `auris-io/src/soundfont.rs`). `loop_passes`' own doc comment only guards `content <= 0`, not an out-of-proportion `loop_end`.

**Fix direction.** Bound the number of passes `loop_passes` can produce — e.g. clamp `total` to `span.saturating_mul(some MAX_LOOP_PASSES)` or cap the iterator length directly — so a malformed `loop_end` degrades to a long-but-finite (or truncated) loop instead of an unbounded one; additionally clamp/validate `loop_end` when an `AudioClip`/`MidiClip` is deserialized (or in `load_project`) so a corrupt file can't carry an absurd value into the graph builder at all.

**Written rule it breaks.** Missing assets are reported, never fatal: the project opens with that one track silent.

### ✅ F-035 · high · Project::split_clip clones bend/controller curves verbatim into both MIDI clip halves instead of rebasing/trimming them like notes, corrupting automation on split.

`crates/auris-core/src/project/clip.rs:988` · correctness · confirmed (executed reproduction; reported independently 2×)

**What a user sees.** Splitting a MIDI clip that has pitch-bend or CC automation drawn on it silently corrupts that automation on both halves: the right piece's curve points keep their original clip-relative tick positions instead of being shifted left by the split offset, so a bend meant to land partway into the new clip now fires near its start (or lands past its end and is dropped); the left piece keeps points that belong past its new, shorter length. A user who splits a phrase with a pitch bend or CC sweep drawn across it hears a wrong or discontinuous bend on playback, with no error or warning — split is one of the most ordinary MIDI editing operations, and note data is handled correctly right next to the broken code, so the corruption is easy to miss in review.

**Trigger.** Draw a pitch-bend or CC curve with at least one interior point on a MIDI clip (e.g. points at ticks 200 and 1200 on a 1600-tick clip), then call `Project::split_clip` at an offset inside the clip (e.g. 800 ticks in). The right-hand piece's `bend`/`controllers` still contain the original points at ticks 200 and 1200, unrebased and un-clamped to the new (800-tick) length.

**Mechanism.** In `Project::split_clip`'s MIDI branch (lines 977-1002), `right = clip.clone()` copies `bend` and `controllers` verbatim, and only `right.notes` is rebased (`split_notes_right(&clip.notes, offset)` at line 992). Nothing analogous exists for curves: no `split_notes_right`-equivalent is ever called on `right.bend`/`right.controllers`, and `left.bend`/`left.controllers` are likewise never truncated to the shorter `left.length` (999). Because `CurvePoint::at` is documented (curve.rs:29) as 'measured from the clip's own start', every bend/CC point that survives in `right` is now off by `offset` ticks (it should have been shifted left by `offset`, and points before `offset` should have been dropped, exactly as `split_notes_right` does for notes) — and any point that was originally on the left side of the cut is duplicated verbatim into the right half instead of being removed.

**Expected.** Per curve.rs's own contract ('at: Where it sits, measured from the clip's own start') and clip.rs's doc for `bend`/`controllers` ('it belongs to the phrase: a clip dragged four bars later takes its bends with it'), a split should rebase and filter each curve the same way notes are handled: the left half keeps only points before the cut (optionally clamped to the new length), and the right half keeps only points at/after the cut, each with `at` reduced by `offset` — mirroring […]

**Fix direction.** Add curve-splitting helpers mirroring split_notes_left/split_notes_right (filter by CurvePoint::at relative to offset, and for the right half subtract offset from each surviving point's at) and apply them to right.bend/right.controllers and left.bend/left.controllers in Project::split_clip's MIDI branch, the same way clip.notes is already handled at lines 992 and 998.

**Written rule it breaks.** CurvePoint::at is documented (curve.rs:29) as measured from the clip's own start; clip.rs documents bend/controllers as belonging to the phrase ("a clip dragged four bars later takes its bends with it")

### ✅ F-049 · high · curve_events omits the leading (0, first.value) event, so a curve's held-flat lead-in before its first point is silently dropped from playback scheduling.

`crates/auris-core/src/project/curve.rs:157` · correctness · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** Any bend/CC curve whose first drawn point isn't at the clip's start plays back wrong: the instrument is heard at the default/last-held value for the lead-in span, then snaps discontinuously to the curve's first value exactly at that point — an audible jump/click — instead of holding that first value from the clip's start as the curve read API and its own doc comment say it should.

**Trigger.** A MidiClip of length 1920 with `bend = [CurvePoint { at: Ticks(480), value: 2.0 }]` (a single bend point placed at beat 2, e.g. a slide the user starts mid-phrase rather than at the clip's very start — an entirely ordinary gesture, not an edge case). `clip.curve_at(ClipCurve::Bend, Ticks(0))` correctly returns 2.0, but `clip.curve_events(ClipCurve::Bend, CURVE_STEP)` returns only `[(Ticks(480), 2.0), (Ticks(1920), 0.0)]` — nothing for ticks 0..480.

**Mechanism.** curve_at() defines a curve as 'held flat outside' its points in both directions — for any `at <= first.at` it returns `first.value` (lines 125-127), and the module doc says the same ('held flat outside them', line 25) and is tested ('flat before the first point', curve.rs:197-200). But curve_events(), which is what actually drives playback, starts its sampling walk at `let mut at = first.at.max_zero();` (line 157) and only ever emits events for `at >= first.at` (the `while at < last.at` loop at 158-161, then the two explicit pushes at 162 and 164). There is no symmetric leading push for the span [0, first.at) the way there is an explicit trailing release push for [last.at, length] (lines 163-164). So whenever a curve's first point is not at clip-relative tick 0, the region before it produces zero scheduled events.

**Expected.** curve_events should emit (or the doc should be corrected): given the doc's own 'held flat outside them' rule and the passing curve_at test for it, a curve whose first point is after tick 0 should schedule an event carrying `first.value` at (at least) the clip's own start, mirroring the trailing release the function already writes at `length` when `last.value != 0.0`.
