### ✅ F-005 · critical · Offline export activates hosted CLAP plugins at the live 512-frame block size while the offline renderer defaults to 1024-frame blocks, silently leaving roughly half of every exported block unprocessed.

`crates/auris-clap/src/bridge.rs:214` · correctness · confirmed (executed reproduction; reported independently 2×)

**What a user sees.** Any offline export/bounce of a project that hosts a CLAP plugin (effect or instrument) is silently corrupted under default settings: the offline renderer's default block size is 1024 frames (auris-engine/src/offline.rs, OfflineOptions::default, block_frames: 1_024) while Session::job_for activates the export's hosted CLAP instances with self.engine.max_block() — the live device's block size, 512 by default (auris-session/src/settings.rs, block_frames: 512). Bridge::render clamps every block to self.max_frames (512), and ClapEffect::process/ClapInstrument::process call it exactly once per graph block with no chunking loop, so only the first 512 of each 1024-frame offline block reaches the plugin. deliver_port then writes only buffer[..512]; buffer[512..1024] is left untouched. For a hosted effect that means half of every block passes through completely unprocessed (raw dry audio, not silence, not a deliberate bypass — just whatever was already in the scratch buffer), producing an audibly alternating processed/unprocessed 512-frame pattern in the exported file. For a hosted instrument the tail is left holding whatever the offline scratch buffer happened to contain between iterations. This reproduces on the default export configuration with no unusual settings required.

**Trigger.** Add a hosted CLAP instrument (or effect) to a track, keep the session's default audio preferences (block_frames = 512, crates/auris-session/src/settings.rs:52), and export the project through the ordinary GUI "Export" command or the CLI `render` command — neither overrides `OfflineOptions::block_frames`, so it stays at the 1024-frame default.

**Mechanism.** `Bridge::render` computes `let frames = buffer.frame_count().min(self.max_frames);` (bridge.rs:214) and every branch that follows — `fill_port` (bridge.rs:265-270, 351-362), `deliver_port` (bridge.rs:327-343) and `silence` (bridge.rs:365-369) — only ever touches `buffer[0..frames]`; nothing loops to cover the rest of a longer buffer. `self.max_frames` is fixed once, at activation, to `ctx.max_block_frames` (bridge.rs:90-122). Activation happens in `Session::job_for` (crates/auris-session/src/session/mod.rs:806-824), which builds its `PrepareContext` from `self.engine.max_block()` — the *live audio device's* block size (session default 512 frames, crates/auris-session/src/settings.rs:52). The offline render that follows is built with a completely independent block size: `OfflineRender::new` (crates/auris-engine/src/offline.rs:246-256) takes `options.block_frames`, which defaults to 1024 (offline.rs:43) and is never reconciled with what any hosted plugin was activated for. Both the GUI export command (crates/auris-gpui/src/ui/commands.rs:2078-2080, `OfflineOptions::whole_project()`) […]

**Expected.** The bridge should be re-chunked (or the plugin re-activated at the render's own block size) so `Bridge::render` always fully services whatever segment size the render graph gives it — e.g. looping internally in `self.max_frames`-sized sub-calls until the whole buffer is covered — exactly as `crates/auris-clap/src/tests.rs`'s `a_shorter_block_than_the_plugin_was_activated_for_still_renders` test already verifies for a buffer *shorter* than the activated size, but nothing in the test suite […]

**Fix direction.** Bridge::render must loop internally over sub-chunks of at most self.max_frames until the whole requested buffer is covered (repeating the per-chunk parameter/note/steady-time bookkeeping correctly), or Session::job_for must activate the export's hosted CLAP instances with the same block size the offline renderer will actually drive (plumb OfflineOptions::block_frames, or clamp to self.engine.max_block(), into the PrepareContext used for export) instead of always using the live engine's block size.

**Written rule it breaks.** "A CLAP plugin sizes its buffers when it is *activated*, from a rate and block size it cannot then be told about again — changing either means deactivating and building it afresh, which only the main-thread half can do." ### ✅ F-008 · critical · Embedded CLAP GUI: if show() fails after set_parent(), HostWindow's Drop destroys the plugin's child HWND before gui.destroy() is called, risking a use-after-free/double-free crash in-process.

`crates/auris-clap/src/plugin.rs:378` · security · confirmed (executed reproduction; reported independently 2×)

**What a user sees.** When a hosted CLAP plugin's GUI `show()` call fails after `set_parent()` succeeded (a spec-legal CLAP outcome, e.g. Surge XT or any JUCE-built plugin under a transient resource/GPU failure), Auris destroys the host container window — which Win32 recursively tears down the plugin's own just-parented child HWND — and only afterward calls the plugin's `destroy()` on a window that no longer exists. Since CLAP plugins run in-process with no sandbox, the plugin's C/C++ teardown code (JUCE, etc.) touching an already-destroyed HWND is a realistic use-after-free/double-free that can crash or corrupt the whole Auris Studio process, not just fail to open one plugin's window.

**Trigger.** Open the GUI of a CLAP plugin that offers only 'embedded' (e.g. Surge XT / any JUCE-built plugin, per this crate's own doc comments) on Windows, where the plugin's `create` and `set_parent` succeed but its `show` implementation returns `false` (a spec-legal CLAP failure — resource exhaustion, a GPU/GL context failure, or any other reason a real plugin's `show` can fail).

**Mechanism.** In `ClapPlugin::open_gui`'s embedded branch (plugin.rs:356-383), `unsafe { gui.set_parent(&mut handle, window) }.map_err(failed)?;` (line 377) makes the plugin's own window a live Win32 child of the host's `container: HostWindow`. `clack_extensions::gui::PluginGui::set_parent` is `unsafe fn` specifically because, per its own doc comment (clack-extensions-0.1.1/src/gui/host.rs, `set_parent`): 'It is up to the caller of this function to ensure that the underlying window object remains valid for the lifetime of this plugin instance's GUI, i.e. up until `destroy` is called.' The very next line, `gui.show(&mut handle).map_err(failed)?;` (line 378), is fallible (clack's `PluginGui::show` returns `Result<(), GuiError>` and fails whenever the plugin's `show` vtable call returns `false` — a legitimate CLAP outcome, not a host bug). If it fails, the `?` unwinds out of the enclosing closure `(|| { ... })()`, which drops the closure-local `container: HostWindow` right there. `HostWindow`'s Drop impl (crates/auris-clap/src/window/win32.rs:127-137) unconditionally calls […]

**Expected.** The container window must not be destroyed until after `gui.destroy()` has returned, matching the ordering the crate already enforces in `close_gui` and in the WM_CLOSE handler, and matching the explicit safety contract stated by `clack_extensions::gui::PluginGui::set_parent`'s own doc comment. The `Err` arm needs to call `gui.destroy(&mut handle)` while `container` (and its Windows child relationship) is still alive, and only then let `container` drop — e.g. by moving destroy() inside the […]

**Fix direction.** In the `Err` arm of `open_gui`'s embedded branch, call `gui.destroy(&mut handle)` while `container` is still alive and its window relationship intact — e.g. move the `gui.destroy` call inside the closure immediately after the `set_parent`/`show` failure (before returning `Err`), or restructure so `container` is only dropped after the outer `gui.destroy(&mut handle)` has run, matching the ordering already used by `close_gui` and the WM_CLOSE handler.

**Written rule it breaks.** // SAFETY: the window was made a few lines up and is owned by this value, which destroys the plugin's GUI before letting go of it. (crates/auris-clap/src/plugin.rs, comment immediately above the `set_parent` call at line ~375-376)

### ✅ F-090 · high · Bridge::render hard-codes `None` for CLAP's transport argument, so hosted plugins never see host tempo, playhead, or transport state.

`crates/auris-clap/src/bridge.rs:306` · spec-mismatch · confirmed (traced through the code; reported independently 1×)

**What a user sees.** Any hosted CLAP plugin that reads host tempo, playhead position, or transport play/loop state (a delay synced to song BPM, an arpeggiator, a plugin drawing a playhead cursor, a tempo-synced LFO) gets no such information and either falls back to a default tempo (typically 120 BPM) or silently does nothing tempo-aware, producing wrong or unsynced output on every project whose tempo differs from that default.

**Trigger.** Host any CLAP plugin that syncs to host tempo or shows/uses playhead position — a tempo-synced delay, a host-synced LFO, an arpeggiator, or a plugin with a position-aware display — while Auris is playing at a tempo other than the plugin's internal default.

**Mechanism.** `Bridge::render` calls `processor.process(&audio_in, &mut audio_out, &events, &mut event_replies, Some(*steady_time), None)` — the final argument is CLAP's `transport: Option<&TransportEvent>`, and it is hard-coded to `None` on every single block (bridge.rs:300-307). `TransportEvent` is exactly the struct CLAP defines to carry `tempo`, `song_pos_beats`/`song_pos_seconds` and the playing/looping flags to a plugin during `process()`. Both callers of `render` throw away the information that would let it build one: `ClapEffect::process`/`process_with_sidechain` (effect.rs:71, :81-88) and `ClapInstrument::process` (instrument.rs:79,85) take `_ctx: &ProcessContext` — underscore-prefixed, never read — even though `ProcessContext` carries `bpm`, `playhead_samples` and `is_playing` for exactly this purpose (auris-core/src/plugin.rs:198-213). Auris's own built-in delay (`crates/auris-dsp/src/delay.rs:235-238`) reads `ctx.bpm` to size a tempo-synced delay line, proving this data is real and meaningful — it simply never reaches a hosted plugin.

**Expected.** Build a `clack_host::events::event_types::TransportEvent` from the `ProcessContext` (`ctx.bpm`, `ctx.playhead_samples`, `ctx.is_playing`, sample rate) each block and pass `Some(&transport)` to `processor.process`, the way the sample-rate and steady-time arguments are already threaded through. `crates/auris-core/src/plugin.rs`'s own doc for `ProcessContext` documents `bpm`/`playhead_samples`/`is_playing` as per-block data every processor needs; a hosted plugin is the one processor in the […]

**Fix direction.** In `Bridge::render`, build a `clack_host::events::event_types::TransportEvent` from the `ProcessContext` (bpm, playhead_samples converted via sample_rate, transport running/looping flags) and pass `Some(&transport_event)` instead of the hard-coded `None`; thread `ctx: &ProcessContext` through from `ClapEffect::process`/`process_with_sidechain` and `ClapInstrument::process` (currently `_ctx`, unused) down into `Bridge::render` so the data has somewhere to come from.

**Written rule it breaks.** A hosted CLAP plugin is two objects, because CLAP's main-thread/audio-thread split is the same one Auris already has ... the ClapEffect it hands out is Send, implements auris_core::Effect, and is the only half the graph ever sees.

### ✅ F-106 · high · Unbounded plugin-reported port/channel/parameter counts size Vec allocations with no cap, letting a buggy or malicious CLAP plugin crash the whole DAW via an OOM-abort or capacity-overflow panic on activation.

`crates/auris-clap/src/ports.rs:110` · security · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** Loading a CLAP plugin that misreports (through a bug, a corrupted binary, or malicious intent) a huge port, channel, or parameter count crashes the entire DAW process outright — `Vec::with_capacity(count as usize)` in `read_side`/`read_params`, and the per-port `vec![vec![0.0; frames]; *port]` allocation in `Bridge::new`, attempt a multi-gigabyte allocation that aborts the process via the global allocator's OOM handler (or panics with "capacity overflow" for the most extreme values) rather than failing gracefully. All work in the project is lost with no save prompt, and the crash happens on plugin activation — one of the most ordinary things a CLAP-hosting DAW does.

**Trigger.** Load and activate a `.clap` plugin (or a buggy build of one) whose audio-ports extension answers `channel_count` with a large value (e.g. `u32::MAX`) for one port, or whose parameter/port `count()` answers similarly large. `ClapPlugin::activate`/`activate_instrument` (plugin.rs `start`, calling `self.ports(...)` at line 501) reaches this on the main thread the first time the user enables the plugin.

**Mechanism.** `read_side` reads `info.channel_count` (a plain `u32` the plugin returns from its `audio-ports` extension, confirmed via `clack-extensions-0.1.1/src/audio_ports.rs:179`) and pushes it unchecked into `channels: Vec<usize>` (line 110), after already sizing that vector from an equally unchecked `count` (`ports.count(handle, is_input)`) at lines 96-97. These become `PortLayout::inputs`/`outputs`. `Bridge::new` (bridge.rs) then does `let room = |port: &usize| vec![vec![0.0; frames]; *port];` (bridge.rs:97) and applies it per port at `input: ports.inputs.iter().map(room).collect()` / `output: ... .map(room)...` (bridge.rs:115-116) -- allocating `*port` separate `Vec<f32>` buffers per declared channel, with no ceiling. The identical pattern (`Vec::with_capacity(count as usize)` from an unchecked plugin-reported `u32`) also sizes the parameter list in `plugin.rs`'s `read_params` (lines 705-707).

**Expected.** The project already treats plugin-reported sizes as untrusted and clamps them before use -- see `window::sane_size` (window/mod.rs:80-85): "A plugin that answers `get_size` with nonsense ... gets a window it can still be found and closed at. Both ends are deliberately generous ... clamping a real answer is worse than passing on a strange one." The same discipline (a sane ceiling on `channel_count` and port/parameter `count`) is missing here, even though `ports.rs`'s own module doc is explicitly […]

**Fix direction.** Introduce a sane upper bound (e.g. a `MAX_PORTS`/`MAX_CHANNELS`/`MAX_PARAMS` constant in the low hundreds to low thousands) and clamp/truncate `count` in `read_side` (ports.rs) and `read_params` (plugin.rs) before it sizes `Vec::with_capacity` or bounds the loop, and likewise clamp `info.channel_count` per port; `Bridge::new`'s `room` closure then inherits the bound automatically since it iterates the already-clamped `ports.inputs`/`ports.outputs`. Treat an out-of-range count the same way the module already treats a port the plugin refuses to describe (via `let Some(info) = ... else`) — degrade to the cap rather than trusting the plugin's raw value.

**Written rule it breaks.** A host must hand a plugin exactly the ports it declared — not the ports the host happens to care about. ... Surge XT Effects is the plugin that taught this crate the lesson ... switching to it took the whole application down. (crates/auris-clap/src/ports.rs module doc)

### ✅ F-330 · high · Hosted CLAP stepped/enum parameters get ParamUnit::Choice with an empty `choices` list, so their picker menu renders with zero selectable options.

`crates/auris-clap/src/plugin.rs:796` · ui · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** For any hosted CLAP plugin with a stepped/enum parameter (oscillator waveform, filter type, LFO shape, and any other non-boolean choice parameter), the DAW picks the "choice" control for it and opens a menu to select an option, but the menu contains only the title row with zero selectable options — `param_choice_menu` loops `for index in 0..descriptor.choices.len()` and `choices` is always an empty slice for CLAP-sourced descriptors. The user cannot pick any named option for that parameter through the UI at all.

**Trigger.** Host any CLAP plugin with a multi-position enum parameter (a filter type, an oscillator waveform, an LFO shape — extremely common; e.g. Surge XT's many mode selectors) and left-click its control in the effect/instrument inspector to open the choice menu.

**Mechanism.** `describe()` assigns `ParamUnit::Choice` to any IS_STEPPED CLAP parameter whose range is not exactly 0..1 (line 779: `(true, _, _) => ParamUnit::Choice`), but always builds the descriptor with `choices: Cow::Borrowed(&[])` (line 796) — nothing in this crate ever populates it. Every other producer of a `ParamUnit::Choice` descriptor in the workspace (auris-dsp's delay sync/distortion mode, auris-synth's waveform picker) goes through `ParamDescriptor::with_choices()`, which sets `steps` and `choices` together (auris-core/src/param.rs:146-153) — auris-clap is the only place that sets the unit without the labels. Downstream, `Inspector::param_choice_menu` (crates/auris-gpui/src/ui/context_menu/tracks.rs:335) builds the picker by looping `for index in 0..descriptor.choices.len()`, not by `descriptor.steps` (which `ParamUnit::Choice`'s own doc comment in auris-core/src/param.rs says is the option count).

**Expected.** A CLAP-hosted Choice descriptor should populate `choices` (even with generic numeric labels such as "0", "1", … when the plugin gives no per-value names) so `param_choice_menu` can list every position, matching the invariant every other Choice-producer in the codebase already keeps between `steps` and `choices`.

**Fix direction.** In `describe()` (crates/auris-clap/src/plugin.rs), when a stepped, non-toggle parameter is classified as `ParamUnit::Choice`, query the CLAP plugin's value-to-text extension for each step (0..steps) to build real labels, or, failing that, fall back to `ParamUnit::Plain` instead of leaving `choices` empty, so the invariant that every other Choice producer keeps (`choices.len() == steps`) is not broken.

**Written rule it breaks.** /// Labels for a [`ParamUnit::Choice`] parameter, in value order. (crates/auris-core/src/param.rs:106) — every other producer of ParamUnit::Choice (`ParamDescriptor::with_choices`) keeps `choices.len() == steps`; auris-clap's `describe()` is the only Choice producer that sets `unit: Choice` without populating `choices`.

### F-122 · medium · `ClapPlugin::open_gui` is a safe fn that lets any caller trigger UB in `owning_window`'s unchecked NSView pointer deref via an arbitrary RawWindowHandle.

`crates/auris-clap/src/window/cocoa.rs:123` · security · confirmed (traced through the code; reported independently 1×)

**What a user sees.** No user-visible harm through today's only call path (auris-session always hands the frontend's own live gpui window handle), but the crate exposes unsound safe API: any safe Rust code — another crate in the workspace, or a future frontend added to auris-clap — can call `ClapPlugin::open_gui(Some(handle))` with an `AppKitWindowHandle` built from an arbitrary or dangling pointer (constructing `RawWindowHandle::AppKit` is itself safe) and trigger a dereference of that pointer as `&NSView` inside `owning_window`, which is instant undefined behavior (dangling/invalid pointer read, potential crash or memory corruption) with no `unsafe` block anywhere in the caller's code.

**Trigger.** Any caller of the public API `ClapPlugin::open_gui(Some(handle))` on macOS where `handle` is `RawWindowHandle::AppKit` with an `ns_view` pointer that is dangling or was never a live `NSView*` (e.g. a handle captured before its window was closed, a handle from a different windowing stack, or a hand-built test handle) triggers undefined behaviour with no `unsafe` block required at the call site.

**Mechanism.** `owning_window` takes a `RawWindowHandle` and does `let view: &NSView = unsafe { handle.ns_view.cast::<NSView>().as_ref() };` (line 123) -- an unchecked raw-pointer dereference whose soundness the comment above it (lines 121-122) attributes entirely to the caller: "the caller vouched for the handle naming a live view -- see `ClapPlugin::open_gui`, which takes it from the application's own window." But `ClapPlugin::open_gui` (plugin.rs:299) is declared as an ordinary safe `pub fn` taking `parent: Option<RawWindowHandle>` -- nothing in its signature or the type system enforces that the `ns_view` pointer is live. On the embedded path, `parent` flows straight from `open_gui` into `HostWindow::open(&plain_title, crate::window::PROVISIONAL, parent)` (plugin.rs:361) and from there into `owning_window` (cocoa.rs:66-68).

**Expected.** A function that dereferences a caller-supplied `RawWindowHandle` cannot itself be safe unless it validates the handle; per the `raw-window-handle` crate's own contract such consumers are expected to be `unsafe fn` (as `ClapLibrary::load` already is, with an explicit `# Safety` section) or to otherwise make the precondition part of the type system, not just a comment on a private helper three call-frames away from the public entry point.

**Fix direction.** Mark `ClapPlugin::open_gui` `pub unsafe fn` (matching the crate's own convention, e.g. `ClapLibrary::load`) and document the real precondition — that `parent` must name a live, still-open window — in a `# Safety` section, or, if the safe signature must be kept, validate the pointer at the boundary (e.g. require callers go through a safe wrapper type that only gpui can construct, or check liveness before deref) instead of trusting a comment.

**Written rule it breaks.** unsafe fn` is how this crate marks a caller-must-uphold-invariant boundary elsewhere in the same crate (`ClapLibrary::load`, library.rs:77), but `open_gui`'s own doc block titled "# Safety of the parent handle" (plugin.rs:293-299) documents only the outgoing handle, never the incoming `parent`'s validity — leaving the actual precondition unstated and unenforced by the type system.

### F-177 · medium · `dropping_a_plugin_closes_the_window_it_left_open` has no assertion after `drop(plugin)`, so it cannot detect a regression in window teardown.

`crates/auris-clap/src/tests.rs:246` · test-quality · confirmed (executed reproduction; reported independently 1×)

**What a user sees.** No user-visible symptom by itself, but a developer relying on `cargo test -p auris-clap` for confidence gets a false sense of coverage: if a future change to `Drop for ClapPlugin` or `close_gui` stopped tearing down the plugin's OS window (e.g. skipped the destroy call, or a refactor reordered drop logic so the window leaked), this test would still pass, and the regression would only surface later as a leaked/dangling OS window when a track with an open plugin editor is deleted.

**Trigger.** A future refactor of `impl Drop for ClapPlugin` that stops calling `close_gui()` (e.g. a field reorder that lets `self.instance` drop before `close_gui` runs, or someone moving the call behind a condition) would leave this test green — it would still not panic, since nothing else in the test observes the GUI state.

**Mechanism.** The test body is:
```
let mut plugin = hosted();
plugin.open_gui(None).expect("open");

```
