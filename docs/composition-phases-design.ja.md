# 作曲エージェントのフェーズ分割 設計案

作曲エージェントの仕事を「作曲」「編曲」「MIX」の三段に分ける設計案です。9節の手順はすべて実装済みで、フェーズ方式が既定です（環境変数での切り替えはなくなりました）。手順4の比較評価は3回まで終えています。

## 1. いまの状態

- デスクトップのエディタのエージェントも、ワークショップの composer も、一つのエージェントが一つの文脈で作詞から MIX までを通しで行う。指示は [composition.md](../crates/auris-agent/src/prompts/composition.md) の 5 段の手順に詰め込まれている。
- 分割の土台はすでにある。`AURIS_COMPOSITION_WORKFLOWS=1` を設定すると、`production_record` の `select_workflow`（composition / accompaniment / vocals / local_edit / delivery）が有効になり、選んだタスクの指示だけが返る（[composition_workflows.rs](../crates/auris-toolbox/src/composition_workflows.rs)）。ただし次の三つが足りない。
  - タスクの分け方が工程になっていない。composition が全部を含み、accompaniment と delivery が一部と重なっている。
  - 指示を切り替えるだけで、何も強制しない。ツールカタログは全部見えたままで、編曲中にメロを書き換えることもできる。
  - 工程ごとの完了条件と、工程から工程への引き継ぎが定義されていない。
- ワークショップには、ホストが `protected_tracks` の変更を拒否する仕組みがある。後述する「前の工程の成果物を固定する」はこの仕組みを広げたものになる。

## 2. フェーズの定義

| | 作曲（score） | 編曲（arrangement） | MIX（mix） |
|---|---|---|---|
| 決めること | 形式、テンポと拍子、キーとコード、歌詞、主旋律、歌声 | 音色、伴奏の各パート、ドラム、演奏表現、セクション転換、SFX | 音量、定位、エフェクト、センド、オートメーション、ラウドネス |
| 書き換えてよいもの | すべて | 主旋律トラック以外の音符（コーラスやハモリのトラックと、その歌唱合成を含む）、すべてのトラックの音色と performance、楽器パラメータのオートメーション、仮のフェーダー | mixer_graph の全体、ミキサーとエフェクトのオートメーション、クリップのゲインとフェード、楽器パラメータ |
| 固定されるもの | なし | 主旋律トラックの音（曲中の位置、音高、長さ、ベロシティ、歌詞）、harmony とセクション、テンポマップ | すべての音符、音色、performance、harmony、テンポマップ |
| 成果物 | 「デモ」：主旋律、コード、ガイド伴奏（ピアノかパッド1本）、歌声のテイク | 全パートが鳴る完成アレンジ | 完成ミックスと、検証済みの書き出し |
| 完了条件（ホストが判定） | セクションが曲全体を覆う。全セクションに harmony がある。主旋律トラックが登録されている（または「主旋律なし」が理由つきで記録されている）。歌ものなら歌詞注記がすべての歌唱フレーズを覆い、テイクが current | 音符のある全トラックに音色がある。ドラムトラックの割り当てが済んでいる。ガイドのトラックが置き換えられたか消されている | 最後の編集のあとに normalize_mix と全体の inspect_audio が current。書き出しを求められていれば verify_render が PASS |

決め方の理由：

- **歌声の合成は作曲フェーズで行う。** 編曲は主旋律と歌詞に触らないので、テイクは編曲後も current のまま残る。作曲の終わりに歌入りのデモを聴けることが、人が判断するうえで最も価値がある。
- **音色の選択は編曲フェーズで行う。** MIX は音色を前提に組むものなので、MIX フェーズで音色を差し替えるのは「編曲へ戻る」操作として扱う。リードの音色も編曲で選ぶ。作曲フェーズのガイド音色は仮のもの。
- **編曲フェーズでもフェーダーは触れる。** 仮のバランスがないと伴奏の密度を判断できないため。インサート、センド、サイドチェイン、normalize_mix は MIX に回す。
- **主旋律に performance をかけるのは編曲の仕事。** performance は非破壊で、音符を変えない。gate、swell、octave_above などで主旋律を処理するのはアレンジの判断にあたる。
- **ガイド伴奏はロール `guide` として登録する。** 編曲で置き換えるか消す前提のトラックで、固定の対象にはしない。
- **主旋律はクリップではなくトラックで登録する。** 編曲でクリップを分割しても ID の付け替えに巻き込まれないようにするため。守るのは曲中の位置で見た音の内容で、ワークショップの `protected_tracks` と同じ単位になる。
- **コーラスやハモリは編曲の仕事。** 主旋律トラックとは別の歌唱トラックとして作るので、編曲フェーズでも `sing` を使える。
- **主旋律のない曲（アンビエントや一部の BGM）も扱う。** 「主旋律なし」を理由つきで記録すれば作曲を終えられ、編曲では harmony とテンポだけが固定される。

`local_edit` はなくす。部分的な修正は「直したいものを担当するフェーズに入って直す」ことで表す。範囲外を守るという規則は、すべてのフェーズに共通の核に入れる。

## 3. 引き継ぎと後戻り

`production_record` を工程の台帳として広げる。

- `select_workflow` を `enter_phase {phase, reason}` に置き換える。前に進むときは完了条件を判定し、満たしていない項目を警告として返す。前進は止めない。止めるのは最後の納品だけ。
- 編曲に入るには、主旋律トラックの登録（または「主旋律なし」の記録）が必要。固定する対象がないと、編曲フェーズのロックが意味をなさないため。ユーザーが持ち込んだ既存のプロジェクトでは、いきなり編曲や MIX から入ってよい。前の工程の完了条件は警告として報告する。
- **主旋律かどうかはエージェントが登録する。** すでにある Role エントリを使い、トラック名や recipe からは推測しない。この点は今の accompaniment の `foreground_clips` と同じ考え方。

### ユーザーが前のフェーズに戻りたいと言ったとき

1. **はっきりした依頼なら、確認せずに戻る。** 「サビのメロを変えたい」「歌詞を直したい」のように、ロックされたものを名指しする依頼は、それ自体が戻る許可になる。エージェントは `enter_phase {phase: score, reason: <ユーザーの発言の引用>}` を呼ぶ。戻る範囲が曖昧なとき（「なんか違う」など）だけ、`offer_choices` で「メロ／歌詞／コード／アレンジ／ミックス」のどれを直すかを聞く。
2. **戻っても後ろの工程の成果は消さない。** 伴奏、音色、ミックスの設定は残り、編曲と MIX の完了記録だけが stale になる。
3. **直す範囲は依頼の範囲に限る。** 依頼の範囲（たとえばサビの 4 小節）を Intent として記録し、それ以外はいつもどおり守る。
4. **直し終えたら、自分で前に進む。** 再び `enter_phase arrangement` を呼ぶと、ホストは変わった小節と範囲が重なるトラックを「要確認」として返す。たとえば次のような場合。
   - コードを変えた小節にある伴奏。generator で作った伴奏は `accompaniment regenerate` で作り直せる。手で書いた伴奏はエージェントが読んで直す。
   - 歌詞やメロを変えた小節の歌声テイク。テイクは stale になるので、作曲フェーズの完了条件として歌い直しが求められる。
   編曲で直し終えたら MIX に進み、normalize_mix と全体の測定をやり直す。デモの時点で止まる規則は、最初の作曲のときにだけ適用し、後戻りでは適用しない。ユーザーが「直したら一度聴かせて」と言った場合は除く。
5. **戻らずにロックされたものを変えようとした場合は、取り消される。** 次の節のガードがその編集を取り消し、「主旋律はロック中。ユーザーの依頼なら enter_phase score」と次の手を返す。エージェントが勝手に主旋律を書き換えることも、ユーザーの依頼を理由なく断ることも、これで防ぐ。

ユーザーが画面で直接編集した結果は、フェーズに関係なくそのまま受け入れる。ガードはエージェントの呼び出しの前後だけを比べるので、ユーザーの編集はそのまま次の基準になる。

## 4. 強制の段階

二段階に分けて入れる。

1. **プロンプトだけで分ける段階。** ツールカタログは今のまま全部見せ、フェーズ別の指示と完了判定だけを入れる。[composition-workflows.ja.md](composition-workflows.ja.md) の「プロンプト実験でツール条件を暗黙に比較しない」という方針を守れるので、legacy との比較が公平になる。
2. **ロックのガードを入れる段階。** ツールごとの許可表は作らず、**実行してから比べる**方式にする。
   - フェーズごとに、固定する状態を「ロック」として定義する（2 節の表の「固定されるもの」）。
   - エージェントの編集コマンドを実行する前と後で、ロックの指紋を比べる。違っていればその編集を取り消し、何が変わったかと次の手（どのフェーズに戻れば変えられるか）を返す。
   - 許可表を使わないのは、`edit_clip` や `layer`、`accompaniment` のように、どのツールが何を変えるかの組み合わせが多く、表がすぐ古くなるため。ガードは「何が変わったか」だけを見るので、新しいツールを加えても漏れない。
   - 置き場所：指紋の計算と比較は、テストできる自由関数として `auris-session` に置く（`auris_session::phase`）。ロックの指定は live コマンドの引数としてセッションに渡し、取り消しもセッションが行う。そうすると、Undo の履歴にもユーザーの画面にも、取り消された編集が残らない。フェーズの状態そのものは会話のメタデータなので、今の `production_record` と同じく `auris-agent` に置く。デスクトップのエージェントと live MCP の呼び出しは、どちらも `ToolHost` を通るので両方にかかる。保存済みプロジェクト向けの `auris-mcp` と CLI にはフェーズがない。
   - 時間のかかるジョブ（`accompaniment`、`arrangement` の apply、`sing`）は、結果を文書に書き込む時点で比べる。
   - カタログからツールを消すことはしない。消すとモデルが「その機能はない」と誤解して、後戻りの判断ができなくなる。

## 5. プロンプトの構成

- **共通の核（約 2〜3KB）。** ID と revision の扱い、単位（bar/beat）、失敗からの回復、誠実さの規律。誠実さの規律はここに一度だけ書く。今の composition.md、live-tools.md、musical-design.md から工程に依存しない部分を集める。
- **フェーズ別の指示。** `enter_phase` の結果と、`production_record` を読んだ結果で返す。今の `workflow_instructions` と同じ届け方にする。置き場所は `auris-toolbox` に一つだけ作る（`composition_phases.rs`）。skill の SKILL.md もこの三段に合わせて書き直し、references はフェーズ別指示の詳細版として位置づける。デスクトップからも `search_documentation` で引けるようにする。
- **フェーズごとに入れる定石（索引だけ。詳細は tool_help と文書に置く）：**
  - 作曲：A メロ／B メロ／サビの役割分担、イントロにサビのフックを使う、落ちサビ、ラストサビの転調、モチーフの反復と展開、歌える音域。
  - 編曲：パートの役割（土台、和声、拍、装飾）と音域の住み分け、ボイシングを歌の音域から外す、キックとベースのリズムを合わせる、フィルとクラッシュによる転換、ビルドアップとブレイク、2番での要素の追加、複製してから変化させる、performance の使いどころ（サビのオクターブ重ね、ハットのゴーストと humanize、swing、strum、swell）、骨組みは generator で作り、印象に残るパートは自分で書くという分担。
  - MIX：まず音量と定位、ベース以外のローカット、キックをトリガーにしたサイドチェイン、ボーカルへのリバーブとディレイのセンド、バスでまとめる処理、セクションごとのオートメーション、最後に normalize_mix。

## 6. 人が確認するポイント

- **エディタのエージェント。** ゼロから曲を作る依頼では、作曲フェーズのデモができた時点で一度止まり、`offer_choices` で「編曲へ進む／メロを直す／歌詞を直す」を出す。依頼が「おまかせ」や「一気に」なら止まらずに進む。止まるかどうかは依頼文から決め、その判断を Intent として記録する。編曲から MIX へは止まらずに進む。
- **ワークショップ。** ディレクターの assignment に `phase` を持たせる。作曲フェーズの候補（デモ 2〜3 本）は通しの候補より軽いので、比較の回数を増やせる。ユーザーが一本を選ぶと、その候補を親にして編曲と MIX を一つの assignment として実行する。今の「選んだ候補から続ける」仕組みがそのまま使える。

## 7. 既存の Workflow との関係

0.x の間は互換を取らずに置き換える。

- `Composition`、`Vocals` → `score`
- `Accompaniment` → `arrangement`
- `Delivery` → `mix`
- `LocalEdit` → 廃止（直したいものを担当するフェーズに入って直す）
- `WritingOrder` → `score` フェーズの引数として残す

## 8. 評価

- `tools/eval/composition_quality.py` の `--prompt-profile` に `phased` を加え、`legacy` / `modular` と同じタスク群、モデル、実行ファイルで比べる。第一段階ではカタログを同じにする。
- 記録するもの：依頼の遵守、盲検での人の好み、失敗したツール呼び出し、トークン数、経過時間。加えて、フェーズ分割で変わるはずの指標：performance 設定の利用数、generator の利用数、主旋律の手戻り回数、転換の数。
- ホストでの拒否（第二段階）は、第一段階とは別の条件として測る。

## 9. 実装の順番

1. 単位表記の矛盾を直す（tool_exposure.rs の「tick-based notes」）。分割とは独立した作業。
2. `production_record` に `Phase`、`enter_phase`、`set_roles`、完了判定を加える。`AURIS_COMPOSITION_WORKFLOWS` の下に置き、プロンプトだけで分ける。指紋と、作曲へ戻った後に「変わった小節と重なるトラック」を返す機能は、どちらも指紋が要るので手順5で入れる。
3. フェーズ別の指示を書き、定石の索引を入れる。共通の核を切り出し、skill を三段に合わせる。
4. legacy / modular / phased を比較評価する。
5. ホストでの拒否を入れ、別の条件として評価する。
6. ワークショップのフェーズ別ラウンドを入れる。
7. 結果が良ければ既定にし、legacy と modular を消す。

## 10. 決まったこと

- エディタのエージェントは、ゼロから作る依頼ではデモの時点で止まる。「おまかせ」「一気に」なら止まらずに進む。
- 編曲フェーズでもフェーダー（gain、pan、mute）は触れる。インサート、センド、サイドチェイン、normalize_mix は MIX に回す。
- ワークショップへの導入は、比較評価の後に行う。
- `AURIS_ARRANGEMENT_HARNESS` の arrangement ツールを編曲フェーズの標準にするかどうかは、評価の結果を見て決める。
- フェーズ別の指示は追記型で渡す。一つのエージェントが一つの会話でフェーズを渡り、システムプロンプトは共通の核のまま変えない。フェーズ別の指示は `enter_phase` の結果と `production_record` の読み出しで返す。評価では、フェーズの境界で会話を区切ってシステムプロンプトを差し替える方式を比較条件として加える。

## 11. 評価の結果（第1回、2026-11-03）

ワークショップのログから新規作曲4件（歌もの3件、インスト1件）を選び、同じ指示・同じ作曲エージェント（Codex gpt-6.1-sol）・同じビルドで、legacy と phased（共通の核＋フェーズ別の指示）を1本ずつ作った。作り直しには `auris-agent` の `workshop_trial` を使った。

| 題材 | 盲検の総合 | 主旋律 | 伴奏 | 聴いた人のメモ |
|---|---|---|---|---|
| 米津玄師風 | phased | phased | 同程度 | phased の歌のほうが自然 |
| Ado風 | 同程度 | 同程度 | legacy | 息継ぎ・編曲も legacy |
| はるまきごはん風 | legacy | legacy | legacy | phased の旋律は良さそうだが、歌声の音域を超えてうまく歌えていない |
| BattleField風（インスト） | legacy | 同程度 | legacy | |

数値（ツールの失敗、時間、サビの持ち上がり）には、どちらの方式にもはっきりした差はなかった。phased は失敗0件、サビの平均の持ち上がりが歌もの3件とも少し大きかった。

読み取れること：

- phased を既定にする根拠はまだない（総合で phased 1、legacy 2、同程度 1）。
- サビを持ち上げる指示が、歌声の音域を超える旋律を生んだ。はるまきごはん風の phased はサビが A4〜F5 にあり、歌えていなかった。主旋律を書く時点で、声の使える音域を知る手段が要る。
- 伴奏と編曲は legacy のほうが好まれた。編曲フェーズの指示（約2.2KB）が、legacy でいつも見えている指示より薄い可能性がある。
- どちらの方式も、イントロとアウトロが短い（今の2倍ほど欲しい）。

1題材1本ずつなので、どの差もばらつきの範囲を出ない。

### 2回目（編曲の指示と arrangement_shape を加えた後）

同じ4題材を、会話つきの指示と自動再開を使う作り直し（`workshop_trial`）で、legacy と phased から1本ずつ作った。新しい編曲の指示は共通の音楽の指示にも入れたので、legacy にも効いている。

| 題材 | 盲検の総合 | 主旋律 | 伴奏 | 編曲・音色 |
|---|---|---|---|---|
| Ado風 | phased | phased | legacy | 同程度 |
| はるまきごはん風 | 同程度 | 同程度 | 同程度 | legacy |
| 米津玄師風 | legacy | legacy | legacy | legacy |
| BattleField風（インスト） | phased | phased | 同程度 | 同程度 |

楽譜の数値は両方式とも1回目より良くなった。歌もの6本中5本で `arrangement_shape` の警告が0件になり、イントロとアウトロはほぼ8小節になった。

読み取れること：

- 総合は phased 2、legacy 1、同程度 1。1回目（phased 1、legacy 2）から逆転したが、1題材1本ずつなのでまだ差とは言えない。
- 主旋律は phased が好まれる傾向（2対1）。伴奏と編曲・音色は、今回も legacy 寄り（phased が勝った題材はない）。編曲フェーズの指示か進め方に、まだ足りないものがある。
- SongEval は、総合で好みが分かれた3ペアのうち1ペアでしか人と一致しなかった（米津玄師風では phased に大きく高い点を付けたが、人は legacy を選んだ）。

### 編曲フェーズの調査（2026-11-04）

2回目の8本について、作曲エージェントのログと完成した楽譜を比べた。phased の伴奏が好まれない理由として、最もはっきりしているのは**作曲フェーズのガイド伴奏が、そのまま完成品のパートとして残っている**ことだった。

| 題材 | ガイド（作曲フェーズの generate_phrase） | 完成品での扱い |
|---|---|---|
| Ado風 | ピアノの chords、96小節 | 同じシードの生成クリップを 11 個に分けて、主な和声パートとして残した |
| BattleField風 | pad、64小節 | 6 クリップに分けて残した |
| はるまきごはん風 | pad、104小節 | 9 クリップに分けて残した（音色は物理モデルのバイオリン） |

### 手順5〜7

- 手順5：ロックの取り消し（4節）。**実装済み。**
  - `auris_session::phase` が、固定された内容の指紋（`Print`）を作る。編曲では主旋律トラックの音（曲中の位置、音高、長さ、ベロシティ、歌詞）、harmony、セクション、拍子、テンポマップ。MIX ではそれに加えて、音符のあるすべてのトラックの音、音色（楽器、サンプルファイル、なぞる元、声）、各クリップの performance。音は曲中で鳴る位置で比べるので、鳴り方を変えないクリップの分割や結合はロックに触れない。ミュートしたクリップは鳴らないので、主旋律をミュートするのは変更になる。
  - `ToolHost` は、`production_record` の今のフェーズから決めたロックを編集のイベントに付けて送る。受け手（デスクトップの `agent_edit_locked`、ワークショップの `execute`）は `Session::agent_command_locked` を通す。前後の指紋が違えば、文書、未保存の印、Undo の履歴を呼ぶ前に戻し、何が変わったかと戻り先のフェーズをエラーとして返す。同じ依頼の中で先にした正当な編集は残る（Undo は依頼を1ステップにまとめているので、Undo では取り消さない）。
  - 時間のかかるジョブ（`accompaniment`、`sing`、`arrangement` の apply、声の切り替え）は、結果を文書に書き込む時点で同じ比較をする（`Session::continue_agent_job_locked`）。デスクトップはジョブを始めたときのロックをジョブと一緒に持ち、ワークショップは歌の各段を `Session::agent_locked` で包む。比較と取り消しは `agent_locked` の1か所にある。
  - 対象外：エージェント自身の undo/redo と、チェックポイントの復元。履歴を動かす操作は、印で元に戻せないため。MIX で音色のパッチを `instrument_state` の中で切り替える（SoundFont の bank/patch など）のは、楽器パラメータとして許している。
  - **作曲へ戻った後の「要確認」も実装済み。** `phase_facts` に小節ごとのダイジェスト（`phase::score_bars`）を加えた。key、コード、セクション、テンポ、拍子の16分ごとの値と、音符のあるトラックごとの、その小節で始まる音符から作る。モデルに返す inspection からは取り除く。後のフェーズから作曲へ戻ると、`production_record` がそのときのダイジェストを覚える（何度か行き来しても、最初に編曲を離れたときのものを使う）。再び編曲か MIX へ進むと、変わった小節（全体のダイジェストか主旋律トラックのものが違う小節）と、そこで鳴っている主旋律以外のトラックを `phase.review` として返す。伴奏そのものの違いは数えない。書き直すことが、ここでの依頼だから。次のフェーズ変更で消える。
- 手順6：ワークショップのフェーズ別ラウンド（6節）。**実装済み。**
  - `Direction` に `phase`（`score` か `finish`）を足した。ないときは、今までどおり一度に完成品を作る。
  - 候補はそれぞれ、曲の隣に `production.json` として production record を残す（チェックポイントにも保存し、復旧ではそれを引き継ぐ）。デモは作曲フェーズから始まる。仕上げは親のデモの記録を引き継いで編曲フェーズから始まるので、デモの主旋律、harmony、テンポは手順5のロックで守られる。役割を登録しないまま終わったデモは失敗として返す。仕上げに要るため。
  - ディレクターの指示には、フェーズ別ラウンドの段落を足す（`auris_toolbox::workshop::director`）。新しい曲ではまずデモを2〜3本出し、選ばれたら仕上げるかメロ、歌詞、コードを直すかを選択肢で聞く。候補カードには「デモ」のバッジが付く。
  - 評価は11節の5回目。
- 手順7：フェーズ方式を既定にした。**実装済み。**
  - 判断の根拠は11節の評価。フェーズ方式の歌もの12本の SAE Arrange は平均76.6で、legacy の73.1を上回り、ロックでの取り消しは一度も起きなかった。
  - legacy の指示（`composition.md`、`live-tools.md`）と `AURIS_COMPOSITION_WORKFLOWS` を消した。システムプロンプトは共通の核（`core.md`）だけになる。`musical-design.md` は曲案と歌詞の生成が使うので残す。
  - 評価ランナー（`composition_quality.py`、`composition_refine.py`）の `--prompt-profile` も消した。記録には `prompt_profile: "phased"` が残るので、以前の legacy の結果とは区別できる。

### 評価の進め方

- 作り直しは `cargo run --release -p auris-agent --example workshop_trial -- <スレッドのフォルダ> <候補ID> <出力フォルダ>`。ワークショップと同じ会話つきの指示と自動再開を使う。1本ずつ順番に動かす。
- **VOICEVOX Engine を起動しておく。** 止まっていると歌の合成が失敗し、候補は最後の書き出しで止まる。デスクトップの VOICEVOX を開くか、`%APPDATA%/voicevox/vvpp-engines/<エンジン>/run.exe --host 127.0.0.1 --port 50021` を動かす。
- 楽譜の確認は `cargo run --release -p auris-session --example song_shapes -- <song.auris>...`。集計と比較のスクリプトは評価フォルダの `scripts/` にある。
- 自動評価は評価フォルダの `scripts/score-gpu.sh <manifest> <出力フォルダ>` で、SongEval、Audiobox Aesthetics、SAE を順に GPU（RX 9070 XT、Windows の ROCm 版 PyTorch）で動かす。1曲あたり SAE 約10秒、SongEval 数秒（初回はカーネルの準備で十数秒）、Audiobox 約1秒。CPU 版の `scripts/score.sh` は1曲あたり約3分半かかる。GPU と CPU の点の差は SongEval と Audiobox で 0.001 以下。結果がそろった評価器は飛ばすので、落ちたら同じコマンドで続きから再開できる。manifest の題材は `theme` に入れる（SongEval は `group` を修正前後の対として読み、同じ group に2曲あると止まる）。
- GPU では、ROCm 7.14 の memory-efficient と flash の attention カーネルが gfx1201 で落ちる（hipErrorInvalidValue）。アダプタは GPU のときこの二つを切る。落ちたプロセスは終わらずに残ることがあるので、`score-gpu.sh` は各評価器に1時間の上限を付けている。半精度は使わない。fp16 は MuQ の出力が全部 NaN になり、bf16 は CPU との差が 0.8 点まで開く。
- 評価器の重みは三つとも学習済みモデルで、環境はメインのチェックアウトの `.local-evaluations/`（GPU 用は三つ共通の `gpu`、CPU 用は `songeval`、`audiobox`、`sae`）。SongEval は transformers 4.46.3 に固定（新しい版では MuQ が動かない）。SAE は pytorch-fast-transformers の CPU 拡張を持たないので、使わない拡張の位置に呼ぶと落ちる代わりの部品を置いてある。公式デモの点（85.7303）を小数4桁まで再現することを確かめた。
- 三つのうち、プロの曲と Auris の曲を分けられたのは SAE だけ（11節の3回目）。SongEval は1回目の盲検で好みが分かれた3ペアすべてで人の判断と逆を向き、Audiobox の PQ はレンダリングのきれいさで Auris が高く出る。勝敗には SAE の Arrange と楽譜の確認を先に見て、SongEval は大きな崩れの確認に使う。SAE はインストでは意味のある点を出さない。
- プロの曲の目安は NAS の既存曲（36曲）。著作権のある素材なので、曲そのものも、曲名や曲ごとの点も、リポジトリに入れない。書くのは平均とばらつきだけ。NAS から読むと1曲あたり7秒ほど余計にかかるので、評価フォルダの `baseline-cache/` に mp3 のまま写し（中身は NAS と同じ）、`baseline/manifest-local.json` から読む。
- 試聴ページは `tools/eval/composition_listening.py` で作る。音源は 24bit PCM に変換してから渡す（浮動小数点の WAV は読めない）。
