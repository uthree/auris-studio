# エージェントツールとワークフロー

[English](agent-workflows.md)

通常の作曲は、利用中のCodexまたはClaude Codeとインストール済みのAurisで進めます。
楽曲を作り、音符を読み返し、レンダーと測定で確認し、必要な修正をして納品します。
内蔵楽器での作曲に評価器の追加導入は不要です。歌声合成には別途対応する歌声音源が必要です。
外部モデルによる音楽評価は、明示的に依頼した[開発実験](development-audio-evaluation.md)として行います。

保存済みプロジェクトのMCP、組み込みのClaude/Codexバックエンド、ネイティブAPIエージェントは、標準的なセッションコマンド、スキーマ、検証を共有します。保存済みの呼び出しには`project`（open_project/create_projectからの絶対パスまたはプロジェクトID）が追加されます。ライブ呼び出しは開いているドキュメントに対して動作し、保存されず、1回のUndoステップを使用します。変更された保存済みの呼び出しは1つのチェックポイントを作成し、読み取りおよび変更されていない設定は保存されません。

安定した数値トラック/クリップIDを取得するには、まず`inspect_project`を呼び出してください。`discover_tools`と`tool_help`は、現在の実行環境で有効になっているツールのみを記述します。保存されたMCP起動グループは`AURIS_MCP_TOOL_GROUPS=manual,mix`（またはトランスクリプション、ボーカル、作曲、すべて）から取得されます。無効なツールは発見およびリストから除外されます。ヘルプには、そのグループが有効になっている必要があると説明されています。すべてのバックエンドにはドキュメント検索機能があります。ネットワーク検索の利用可能性はバックエンドおよび権限ポリシーによって異なります。実行レジストリは、名前、説明、スキーマ、ディスパッチをまとめて提供します。

ライブバックエンドには、`BRAVE_SEARCH_API_KEY`が空でない場合にのみ`search_internet`が含まれます。Claude、Codex、rigで共通のホスト、ランタイムの発見/ヘルプ、ネットワーク権限ゲートを使用します。送信されるスキーマとデフォルトの`tool_help`レスポンスは、説明的なフィールドの説明を省略しますが、すべての検証制約は維持します。選択された操作のフィールドの完全な説明と例については、`name`と`operation`（例えば`mixer_graph`、`set_strip`）を含む`tool_help`をリクエストしてください。

<a id="exact-authored-notes"></a>
## 明示的に作成したメモ

作成した主旋律に生成伴奏を付けるには、[`accompaniment`](agent-accompaniment.ja.md)を使用します。これは明示的なメロディクリップIDを保護し、伴奏をAurisライターに委ね、1回の編集で選択した伴奏クリップのみを再生成しながら和音を変更できます。`manual`および`composition`グループの両方で利用可能です。和音を修正する前に、`suggest_harmony`は選択されたメロディを読み取り、小節ごとの理由、緊張、そしてシンプルな代替案を含む短い進行を提案します。ムードによって、対応する音色を使う価値の基準が変わります。7度、sus4、ディミニッシュコードの割合は必要ありません。提案の修正と和音オブジェクトは、選択的伴奏再生成に渡すことができます。これは読み取り専用で、同じ2つのツールグループで利用可能です。

明示的な種別と名前を持つトラックを追加し、次に、その数値トラックID、目的のクリップ名、1ベースの`start_bar`、および長さ`bars`を持つ`add_clip`を追加します。返された`clip` IDでクリップを読み取り、所有者`track`は使用しないでください。`inspect_project`は`tracks[].track`と`tracks[].clips[].clip`を使用し、作成結果とツール引数に一致します。これらは異なる数値アドレスであり、位置的トラックID付けや明示的なトラックからクリップへの変換は行いません。編集する前に`read_notes`を使用してください。1から8つの異なるクリップページには`clips:[{"clip":2},{"clip":3,"offset":128}]`を供給してください。レスポンスには、トップレベルの`revision`と、1つの`clips`配列を含みます。各ページには最大128のノート、正確なティック、正規化されたベロシティ、元のストレージインデックス、`truncated`、`next_offset`が含まれています。ページ間で編集せずに、各クリップの次のオフセットに従ってください。インデックスは0から始まり、供給されたバージョンと照合されます。

`edit_notes`は、トップレベルの`expected_revision`と、入力された`input`オブジェクトを1つ受け取ります。`input.kind="inline"`は、1〜16のクリップエディットのバッチを受け取ります。パッチは更新/削除用の元のインデックスを処理し、新しいノートを追加します。置換では完全なノートリストを指定し、[]はそれをクリアします。更新はボーカルメタデータを保持します。両方の形式は、クリップカーブ、パフォーマンス、レシピ、再生ウィンドウを保持します。

```json
{
  "expected_revision":"<revision from read_notes>",
  "input":{"kind":"inline","edits":[{"kind":"patch","clip":2,
    "update":[{"index":0,"velocity":0.7}],
    "add":[{"pitch":62,"bar":3,"beat":2.5,"length_beats":1.5,"velocity":0.8}]}]}
}
```

位置はティックではなく音楽的な単位で指定します。`bar`は曲全体での1始まりの小節番号で、`add_clip`や`edit_harmony`と同じ番号です（クリップ先頭からの数ではありません）。`beat`はその小節内の1始まりの拍で、拍子の拍（4/4なら4分音符、6/8なら8分音符）で数え、細分は小数で表します（`2.5`は裏拍、`2.25`は16分、`2.333`は3連）。`length_beats`も同じ拍で数え、小節線をまたげます。発音位置は拍の1/8までの通常の細分か1/6までの3連の上にある必要があり（1/100拍以内なら正確に吸着）、その間の位置は最寄りの候補を示して拒否されます。ノリはずらした発音位置ではなくスウィングやヒューマナイズの演奏設定で付けてください。読み取りも同じフィールドを返し、各クリップの`bars`を`[最初, 最後]`で示し、編集では拒否される位置にある既存の発音（録音や取り込み）には`on_grid: false`を付けます。ノートはクリップに適合し、正の長さ、MIDIピッチ0..127、ベロシティ0..1を有する必要があります。すべての変更は単一の原子編集前に検証されます。古いリビジョンはノートを変更せずに拒否されます。インライン入力は4096回のノート変更を許可します。より大規模なスコアの場合は`input:{"kind":"file","source_path":"/absolute/notes.json"}`を選択してください：最大16 MiB、65536回のノート変更を含む、同じクリップ編集配列を含むローカルのUTF-8 JSONファイルです。ホストはそれを一度読み込み、ライブ実行前にその不可変のドラフトを承認します。入力は資産として保存されることはありません。

<a id="live-request-history"></a>
## ライブリクエスト履歴

デスクトップは、1つのユーザーリクエストによる編集を、既存のSessionのUndoスタック内で1つにまとめます。ジェスチャーを開いたままにしたり、再生を遅延させたりはしません。`history`はライブ専用です。`{"operation":{"kind":"read"}}`は、上限付きのUndo/Redoエントリ、各方向で利用可能な`available_group`、および数値の`revision`を返します。`{"operation":{"kind":"undo","group":2,"expected_revision":123}}`でそのグループを正確に取り消します。`redo`も同じフィールドを持ちます。以前のノート配列を再構築する代わりに、これを使用してください。人間による編集と開いているジェスチャーは境界になります。古いグループや中断されたグループは拒否されます。空のリクエストはステップを追加しません。チェックポイントは別名のマイルストーンとして個別に扱われます。

<a id="arrangement-curves-and-timeline"></a>
## レイアウト、曲線、タイムライン

`AURIS_ARRANGEMENT_HARNESS=1`を使用する場合、`arrangement`を使用して機能とフレーズ条件を確認し、制限付きのセクション固有の提案を作成し、その正確な計画を1回のUndo編集として適用します。[arrangement proposals](arrangement-harness.ja.md) を参照して、ボイシング変更／レイヤー、対象範囲を限定したオートメーション、SFXアライメント、権限、検証をご覧ください。

`edit_clip`は、`clip`と、`kind`を持つ型付きの`operation`を受け取ります。移動・コピー・分割・サイズ変更の位置には、絶対タイムラインのティックを使います。コピーはソースを保持し、オプションの転記はコピーされたレシピのみを凍結します。サイズ変更は保存されたMIDIノートを再生成することなく再生ウィンドウを変更します。`freeze_recipe`はスコアを保持し、レシピを削除します。`bake_performance`はパフォーマンスをノート/曲線に明示的にコミットします。オーディオ操作では、ゲイン、録音テンポ、テンポフォロー、ソースフレームフェード、クロスフェードが表示されます。分割、コピー、削除後にIDを再度読み取ります。

`edit_clip_curve`は、作成されたベンド/コントローラーレーンを読み取りまたは編集します。サステインの場合：

```json
{"clip":2,"curve":{"kind":"controller","number":64},"operation":{"kind":"read"}}
```

返送されたリビジョンを`expected_revision`にコピーし、次に`merge`、`replace`、または`clear`を使用します。ポイントには`at_tick`と`value`が含まれています。コントローラー値は0..1に正規化され、ベンドは半音を使用します。位置はユニークでクリップ内に位置する必要があります。派生パフォーマンスおよびその他の作成されたレーンは保持されます。

`edit_timeline`は位置付けられたテンポおよびメトロポイントを読み取りまたは編集します。位置は絶対ティックを使用し、ノートの位置は変更されません。読み取り結果にはネイティブのBPM範囲が含まれます。メトロポイントの分子は1〜32、分母は1〜32の範囲内の2のべき乗です。1ベースのバー再生範囲を使用する場合は`set_loop`を使用してください。

<a id="sound-search-controls-and-mixing"></a>
## サウンド検索、コントロール、ミキシング

`search_instruments`は、1つの`request`オブジェクトを処理します。対象モードは、クエリ付きの`text`、参照ID付きの`similar`、または範囲指定の`browse`です。各モードはソース/ライブラリフィルターと最大50件の結果をサポートします。テキスト/ブラウジングはオフセットページングをサポートします。返されたIDを`set_instrument`のsound_idにコピーします。IDにはスコープがあり、更新、ライブラリの識別情報の変更、追い出し、再起動で期限切れになります。音響インデックス作成はバックグラウンドで実行されます。インデックス付け中は他の作業を続け、後で再試行してください。`instrument_diagnostics`は再スキャンせずに既存のスキャンおよび測定エラーをページングします。レスポンス内のライブラリインデックスはサウンドIDではありません。

`inspect_instrument`は、ネイティブパラメータキー、範囲、選択プレビュー、値、およびオートメーションフラグを返します。`set_instrument_params`は、数値のトラック、パラメータ、値を含む1つの制限付き`edits`バッチを受け付けます。1つのパラメータは1要素のバッチです。重複するターゲットや無効/離散的な値は原子的に拒否されます。既存のパラメータオートメーションは保持され、再生中に定常値を上書きすることがあります。

`mixer_graph`は、すべてのバックエンドにおける単一のミキサーエントリポイントです。アクションでタグ付けされた`operation`オブジェクトを1つ渡します。`read`から開始し、安定したトラック/エフェクトノードIDをコピーします。`set_strip`は、供給されたgain_db、pan、mute、またはsoloフィールドのみを変更します。track:masterはgain/panを受け付けます。`set_outputs`は目的を原子的に置き換え、`connect`はブランチを追加します。`add_send`は、初期レベルとプレ/ポストフェーダータップを1回の編集で設定し、`set_send`は返されたsend IDを使用します。`set_sidechain`は検出器ソースを置き換えまたはクリアします。アクションはエフェクトの追加/削除/移動/有効化、およびネイティブパラメータの読み取り/設定を追加します。すべての接続はDAGを形成する必要があります。[Mixer signal flow](mixer-graph.ja.md)を参照してください。

測定には数値オーディオ検査を使用し、一般的なソースフェーダーの移動が適切と思われる場合はnormalize_mixを使用してください。相対的なバランスを保ち、フェーダーまたはピークの制限まで停止できます。サウンドリプレースメントはフェーダーを保持しますが出力レベルを大幅に変更することがあるため、再度測定してください。オーディオファイルを渡しても再生が確立されるわけではありません。

`automation`は、入力されたターゲット（`track_gain`、`track_pan`、`master_gain`、`master_pan`、`send`、`instrument`、または`effect`）と操作を選択します。`read`は、ポイントと選択肢をネイティブ単位でページングします。`expected_revision`にそのバージョンをコピーし、`set`または`clear`に使用します。`set`は最大4096個の`{at_tick,value}`ポイント、オプションの`replace`および`curve`（`linear`または`hold`）を受け付けます。絶対ティック、離散的なパラメータステップ、およびすべてのポイントは、変異前に検証されます。静的コントロールは変更されません。

<a id="audio-and-midi-delivery"></a>
## オーディオとMIDIの配信

`checkpoints`は名前付きスナップショットをリストアップし、新しい名前付きスナップショットを作成したり、既存のスナップショットを復元したりします。操作種別`list`、`create`、または`restore`を使用してください。復元には`expected_revision`から`inspect_project`を使用し、現在のファイルパスを保持し、1回のUndoステップです。指定されたバージョンとワーカーの所有権の両方がチェックされるため、読み込み中に行われた関係のない編集は保護されます。既存のチェックポイント名は一切変更されません。スナップショットは資産参照を保持し、オーディオファイルは複製されません。

`import_audio` と `import_midi` は、既存の `at_tick` のドキュメントに追加されます。どちらも絶対ローカルの `path` を使用し、現在のテンポ／拍子マップを保持し、コピー/デコード/パース作業を UIスレッド外で実行します。オーディオインポートは独立したソースコピーを保持し、オプションの `name` が新しいトラックにラベルを付けます。MIDI インポートはノート、ベンド、コントローラーのタイミングを保持し、音色の確認が必要な既定の楽器を使用します。キャンセルまたはドキュメントの変更は結果を破棄します。各インポートは1回のUndoステップになります。

`render`は、現在のスナップショットを絶対パスを持つ`mix`のターゲット種別または絶対フォルダを持つ`stems`のターゲット種別にエクスポートします。オプションの範囲はstart_bar/barsを使用します。ビット深度は16、24（デフォルト）、または32ビットです。`preview`は、必要な範囲（最大120秒まで）の保護された24 kHz WAVを作成します。`export_midi`は、スコアを出力に書き込みます。`verify_render`は、既存のパスを音量/ピーク/終了値の制限に対して測定します。

エージェント `render` は整数エンコーディング前に正確に要求された波形を測定し、`ceiling_db`（デフォルト -1 dBTP、範囲 -12..-0.1）に必要な場合にのみ減衰を適用します。`source_true_peak_db`、非正の `attenuation_db`、実際のエンコードファイルの上限値および測定値を返します。これはドキュメントやミキサー、ノート、ダイナミクス、または長さを変更しません。これはリミッターやボリューム正規化ではなく、均一な出力ゲインです。ステムは相対的なレベルを維持するために同じゲインを共有します。音量の小さい書き出しは変更されません。以前のミックス測定はレイアウト編集後に古い値になり得ます；エクスポートされたバイトは公開前にチェックされます。ピーク保護はボリュームターゲットが到達することを防ぐことができ、実際の結果を確認し、両方のターゲットが通過したと主張するのではなく、その制約を報告してください。すべてのバックエンドは同じ契約を使用します；保存済みの呼び出しはプロジェクトを追加します。作業はUIスレッド上で実行され、プライベートステージは変更されていないキャンセルされていないドキュメントに対してのみ公開されます。既存の出力ファイルは拒否されます。エクスポートではプロジェクトの保存や元に戻すステップは追加されません。例と測定結果については [Audio delivery](agent-audio-delivery.ja.md) をご覧ください。

<a id="generated-phrases"></a>
## 生成されたフレーズ

`generate_phrase`を使用して、生成されたMIDIクリップを既存の楽器またはドラムトラックに追加します。たとえば、`{"track":1,"part":"lead","start_bar":5,"bars":4,"seed":42}`は5小節目から始まる4小節を書き込みます。パートは`lead`、`chords`、`pad`、`arp`、`bass`、`drums`、`kick`、`snare`、`hat`です。`start_bar`は1ベースです；`bars`は1..1024です；`seed`はデフォルトでゼロです。メロディックパートはプロジェクトのキーとコードを使用するので、まず`edit_harmony`でハーモニーを書き込みます。ドラムパートはドラムトラックのサウンド割り当てを使用し、コードは必要ありません。

結果には新しいクリップID、ノートの数、シードが報告されます。クリップは生成レシピと保存されたノートを保持しているため、通常のクリップコントロールを通じて編集または再生成できます。

`edit_recipe`は、1〜16の明示的なクリップIDを読み取り、パッチを適用し、再生成します。`patch`は、指定されたレシピ設定のみを変更します；`regenerate`は、同じもの、次のもの、または明示的なシードを選択します。どちらも保存されたノートを再生成します。`subdivision`は、`eighth`、`sixteenth`、`eighth-triplet`、`sixteenth-triplet`のいずれかであり、保持されたノートの長さではなくグリッドを設定します。`rhythm`はグリッドのステップを繰り返します。`x`はヒット、`X`はアクセント、`o`はゴースト、`.`/`~`/`-`は休符、スペース、タブ、`|`区切り文字を任意で使えます（例：`x...x...`）。空欄はパターンをクリアします。ノート数と保持時間を設定するには、`density`と`gate`を使用します。enumとリズムの制約は、すべてのバックエンドに送信されるコンパクトなスキーマに残ります。手動で編集されたノートには`replace_hand_edits:true`が必要です；それ以外の場合、完全なバッチは拒否されます。オプションの`drum_voice`は、単一のドラムレーンを選択します。`set_drum_assignment`は、ノートやその他のマッピングを書き直すことなく、ドラムロールのMIDIノートを変更します。既存のクリップは保持され、1回のUndoステップで新しいフレーズが削除され、ドキュメントは保存されていないままになります。同じツールは、共有されたライブカタログと権限チェックを通じて、ネイティブモデルAPI、Codex、Claude Codeにも利用可能です。読み取り専用モードとプランモードは生成を拒否します。

<a id="non-destructive-performance"></a>
## 非破壊パフォーマンス

パフォーマンスコントロールを変更する前に、MIDI `clip` ID を使用して `inspect_performance` を呼び出してください。`set_performance` を使用する場合は、部分的な `settings` オブジェクト（例：`{"clip":2,"settings":{"swing_percent":62,"gate":0.8,"expression":{"timing":0.15}}}`）を使用してください。提供されるフィールドのみが変更されます。ファミリー内では、最初の一致するステージがその場で編集され、他のステージは順序を維持します。保存されたノート、生成レシピ、作成されたコントローラーカーブ、自動ボリュームコントロールの形状はそのまま残ります。ライブホストはユーザーの要求に応じて変更された呼び出しをグループ化し、現在の設定を繰り返すことは履歴を追加しません。結果は設定を読み返します。

`note_effects`は、実際の演奏処理を通る最初のループパスを測定し、最大2048のノートと32のステージを使用します。変更されたオンセット、長さ、ベロシティ、ピッチ、追加/削除されたノート、同時コードグループ、警告、および明示的な切り捨てを報告します。ストラムは同時ピッチを広げます：単一ノートのアルペジオは、イベントを変更しないストラム設定を保持できます。その場合は、有効なストロークを主張しないでください。ピッチカーブ、トーンカラー、ボリュームコントラストはノートイベント測定の範囲外です。`pitch_effects`はコントローラーの変更を別々に報告します。`drum_voice`を選択して、指定されたライターのステージを確認します。クリップ全体の測定は、内側のスコープを測定する前に停止します。四分音符64拍を超えるクリップ上のタイムグリッドジェネレーターも測定を停止するため、間隔の広い長いクリップでは、検査スキャンが曲全体のグリッドをスキャンすることはできません。

`settings.slide`を選択すると、短い離散的な中間ノートが生成されます。これは、明確な単音ラインを、少なくとも2半音の動き、重なり合うノートの有無、四分音符1拍を超える間隔がない状態で接続します。`note_effects`は挿入されたノートとトランジション条件を報告します。挿入されたノートがゼロの保存強度は、有効なスライドではありません。

連続したピッチ接続には`settings.pitch.glide_ms`を選択してください。ゲートおよびタイミングエディット後の最終的に演奏されたノートを追います。ノートは独立して分離され、長さは少なくとも80ms、間隔は最大60ms、2オクターブ以内である必要があります。繰り返されるピッチにはピッチ移動は必要ありません。独立した`pitch_effects`レポートは、グライドのみを無効にした状態で実際の結合されたベンドを比較し、作成されたベンドやその他のジェスチャーを保持します。したがって、動作中のグライドとすでに存在していたベンドを区別します。不完全な測定は不明であり、成功や効果がない証拠ではありません。診断は最初のループパスのみを説明します。

各`pitch_effects[].report`は、そのトップレベルの`effective`を`control: "glide_ms"`の貢献としてラベル付けします。`generated_curves.bend`はその同じ孤立した貢献を測定し、`all_bend_gestures`はそのステージにおけるすべての曲がりジェスチャーを測定します。`modulation`と`volume_swell`は対応するコントローラーを別々に測定します。各比較はその制御のみを無効にし、他のステージや作成された曲線を保持します。`measured: false`と`effective: null`は未知を意味します。曲線処理は2,048のソース/実行ノート、32のステージ、四分音符64拍、30秒、2,048の比較タイムスタンプに制限されます。`instrument_response: "unknown"`はパッチの応答を確立するためにオーディオチェックが必要です。対象となるものには、テンポマップからの`maximum_gap_ms`と`gap_limit_ms`が含まれます。休止符の説明では、ビートラベルからその長さを推測する代わりに、これらの測定値を使用してください。

別の`inspect_performance`呼び出しで読み返してください。アーティキュレーションに効果がない場合は、譜面を書き直したり意図的に休止符を埋めたりせずに、その条件を説明してください。オーディオ応答を確認する際は、特にコントローラーマッピングが不明なホストパッチの場合、前後の同じ短いレンダリング範囲を比較してください。変更されたコントロールカーブやオーディオ信号は、音楽的品質の判断ではありません。ローカルの`inspect_audio`およびパフォーマンス診断は、この機械的検証をカバーします。別の評価モデルは必要ありません。

コントロールには、人間化、スイング/グリッド、ゲート、ミュート、ブラシ、スライド、トランスポレーション、リーンの、オクターブコピー、エクスプレッション、ストラム、ゴーストノート、自動ピッチ、リファレンスグルーヴが含まれます。比率は0..1を使用し、スイングは50..75パーセントを使用します。タイムコントロールは、`lean_ticks`（四分音符あたり960ティック）を除くミリ秒を使用し、ピッチの深さとトランスポレーションは半音を使用します。ツールスキーマは各フィールドの範囲とenum値を提供します。ピッチとオクターブジェスチャーにはメロディック楽器クリップが必要です。ステージを明示的に削除するには、例として`{"clip":2,"settings":{"reset":["swing","expression"]}}`のような`reset`配列を渡します。

検査官から正確な`drum_voice`の名前を渡すと、ドラムキット内の1つのライター（例：`{"clip":3,"drum_voice":"Hat","settings":{"expression":{"velocity":0.2}}}`）を編集できます。グローバルパフォーマンスおよびその他のドラムのライターは保持されます。`drum_voice`を省略すると、クリップのグローバルスタックが編集されます。参照グルーブの場合、まず`{"groove":{"reference_clip":4,"timing":0.8,"velocity":0.3}}`を`settings`内に設定します。キャプチャでは、参照クリップの16分音符グリッド上の最初の実行パスが使用されます。後の強度編集はそのスナップショットを保持しますが、ソースを変更すると再キャプチャされません。

これらのツールは、保存されたMCPおよびライブネイティブモデルAPI、Codex、Claude Code間で標準的なカタログを共有しています。読み取り専用モードとプランモードでは、検査を行い、編集を拒否できます。[real backend validation](agent-performance-validation.ja.md) を参照すると、実際のレンダリングやUndo/Redoチェックを含む、完了したCodexおよびClaudeのトライアルを確認できます。

<a id="live-harmony-and-vocals"></a>
## ライブハーモニーとボーカル

外部で用意したノートJSONは `import_transcription` で取り込めます。インラインの `transcription` または絶対パスのJSONファイル `path` を1つ指定します。`at_tick` で挿入位置、`name` でピアノトラック名を指定できます。検証と権限については [外部ノートAPI](transcription-api.ja.md) を参照してください。

新しい曲の場合、その音楽的決定を`edit_harmony`（例：`{"start_bar":1,"bars":16,"key":"D major","chords":"| I | vi | IV | V |"}`）を含むドキュメントに記述してください。チャートは指定されたバー間で繰り返されます。範囲終了後は前のキーが再開され、既存の内側キーポイントは保持されます。この操作はキー/コードマップを編集し、ノートとミックスを保持し、Undoステップです。可聴可能なコードノートだけでこのマップにデータを入力することはできません。`clear_chords:true`は選択された範囲をクリアします。クリアする際は`chords`は省略してください。

フォームをセクションのレーンにも書き込みます。例えば、`{"start_bar":1,"bars":4,"section":"Intro"}` と `{"start_bar":5,"bars":8,"section":"Chorus"}` は、キーやコードの変更なしで有効な `edit_harmony` の呼び出しです。ラベルはその要求された範囲を覆い、内部セクションの変更を置き換え、範囲の後に前のラベルを復元します。ラベルは空欄でなく、最大 256 バイトの UTF-8 バイトで構成され、制御文字を含まない必要があります。ノートとミックスは保持され、1 つのUndoステップで範囲編集を元に戻します。新しい曲を作曲する際は音楽に適したセクションを計画し、`inspect_project` でその位置を確認してください。クリップ名や文章の概要はセクションメタデータを作成しません。短いループは同じセクションに残すことができます。

<a id="live-vocal-production"></a>
### ライブボーカル制作

共通ハーネスは、短縮形式の制限なしで新しいボーカル・楽曲リクエストを完全な楽曲として扱います：2番目のアウトロと後続のコーラス／エンディング、そして1番目のアウトロを計画し、書き込みます。明示的な長さ、1コーラスのデモ、抜粋、ローカル編集は、リクエストされた範囲を維持します。ノートを書く前に実際のセクション範囲を計画します；後続のアウトロには、意図的なメロディの再利用と伴奏の変更を加えながら、独自の歌詞と物語展開を与えます。1番目のアウトロのスケッチは中間結果です。このガイドラインは、デフォルトおよび実験的なプロンプトプロファイルの両方に適用されます。

`inspect_singer`には、選択されたボーカルまたはレンダリングされたテイクがない場合でも`section_coverage`が含まれています。名前付きセクションは、ノートアタック、歌詞を含むノート、フォニーム割り当て、継続マーカー、割り当てされていないノート、クリップループからのアタックを報告します。`section_coverage.next_section_offset`を`section_offset`として使用すると、最大32セクションまでの次のページを読み取ることができます。これはスピーカーリスト`offset`とは独立しています。明示的なセクションの終了には、現在の楽譜を超えた計画された後部セクションが含まれます。`unbounded_last_section`は、推測可能な正の範囲がない最終ラベルをマークします。カウントは、ミュートされていないクリップでの作成されたオンセット、演奏前のものを含みます；持続するノートは、開始する部分のみをカウントします。`track_muted`はトラック状態を別々に報告します。検査は読み取り専用であり、ノートチェックはページあたり100,000まで制限されます。`analysis_complete:false`を含むセクションは部分的なカウントを持ち、不在を証明することはできません。

計画された歌唱セクションとカバーを比較し、実際のノート/歌詞を読み返してください。空のインストルメンタルイントロダクション、ブレイク、エンディングは有効です。ループした歌詞は新しい作られた2番目のコーラスを確立しません；肯定的なカウントや現在のテイクだけで完全な歌詞、正しい発音、または音楽的品質を確立するものではありません。リクエストがあれば完全な楽譜を合成してください。合成がブロックされた場合は、楽譜を保持し、具体的な未完成の作品を報告してください。

[歌唱フォームのスモークテスト](../tools/eval/references/vocal-song-form-v1.json) エクササイズは、指定されていない曲と16バーの1コーラスリクエストを実行します。`composition_quality.py run --manifest tools/eval/references/vocal-song-form-v1.json --no-candidate-tools --repetitions 1` と通常の実行可能ファイル/出力引数で実行してください。[記録済みのスコア検査](../tools/eval/references/vocal-song-form-validation-2026-10-24.json) は初期完了と再生をチェックしますが、歌唱や聴取品質を評価するものではありません。

`edit_vocal_notes`は、1〜256個の指定された歌詞、フォニーム、タイミングピン、またはピッチオーナメントの修正を1人の歌手クリップに適用します。`read_notes`から`expected_revision`を供給してください。`inspect_singer`は、手動フォニーム/タイミングのサポートとモデルフレームホップを報告します。サポートされていないコントロールは拒否されます。ノート/フォニームインデックスが存在している必要があります。スクープ/フォールとビブラートは元のピッチ、長さ、ベロシティを保持します。バッチ処理に失敗した場合、すべての修正が元に戻されます。レンダリングされたスコアを変更した後、`sing`を再度実行してください。

`singer` のトラックとノートクリップを作成し、`edit_notes` でそのメロディーを追加します。`list_voices` は16ページ分のインストール済みのボイスエントリを検出します。`next_offset` を参照してください。検出はモデルの検証やダウンロードは行いません。`set_singer_voice` で、返送された絶対的な `voice` パスと数値の `track` ID を使用します。オプションの `speaker` は名前付きスタイルを選択します。`inspect_singer` は選択されたボイス、利用可能なスピーカー名、および再生状態を読み返します。スピーカーリストは128名のページです。`next_offset` を参照し、`offset` でさらに読み取ります。スピーカーを変更するには、選択されたボイスパスを希望する名前で繰り返します。無効な名前やモデルは前の選択を維持します。読み込みと推論は既存のローカル自動アクセスポリシーを使用します：ネットワーク/デバイスモデルパスやリモートの VOICEVOX URL は拒否されます。ローカルのループバック VOICEVOX はサポートされており、そのエンジンはすでに実行されている必要があります。

`write_lyrics`は`clip`と`text`、例えば`{"clip":2,"text":"さくらさいた"}`を読み取ります。仮名は mora と音素に分割され、非仮名テキストにはインストール済みの日本語辞書が必要です。最も早いノートから開始するには`from`を省略するか、時間順に`read_notes`からゼロベースのストレージインデックスをコピーしてそこから開始します。保存済みの呼び出しとライブ呼び出しは同じストレージインデックスを使用します。後で記入されていないノートはその単語を保持します。返信された`filled`のカウントと`available`の容量を確認し、フレーズ全体が入力されたことを確認する前にノートを読み返してください。

歌手の`track`とオプションの`seed`を組み合わせて`sing`に呼び出し、実際の再生テイクを作成します。省略した場合、前のテイクのシードは保持され、最初のテイクには0が使用されます。`inspect_singer`は完了時に`take_state:"current"`、合成前に`"missing"`、譜面またはボーカルが変更されたときに`"stale"`を返します。一時的なガイドボーカルは完了したボーカルテイクではありません。ボーカルの検出、読み込み、合成、WAVステージングはUIスレッド上で実行されます。会話を停止すると保留中の作業がキャンセルされ、変更されたドキュメント、置き換えられたボーカルの読み込み、取り消された権限はその結果を受け入れることができません。明示的なエージェント作業は、作業が完了するまで自動的な歌手レンダリングを一時停止します。選択、歌詞、完了したテイクは別々のUndoステップとして処理され、保存されません。合成はセッションの作業フォルダでオーディオをステージングします。

これらのライブオペレーションはすべて、リグ、Codex、Claude Codeに対して同じ権限ゲートを使用します。読み取り専用/プランモードでは、ボーカルをリストアップしたり歌手を確認したりできますが、ハーモニーの編集、ボーカルの選択、歌詞の作成、または歌唱テイクの適用はできません。エラーはモデルに返信され、成功した楽曲制作として報告されることはありません。

## 保存済みプロジェクトの作曲

MCPは完全な保存ファイルツールカタログを保持します。以下のファイルベースの作曲、レンダリング、再生ワークフローがMCPを説明しています。


MCPは保存されたプロジェクトコマンドを`auris-toolbox`を通じて公開します。一般MIDIライブラリ、ボーカルライブラリのパス、プロジェクト再生状態を確認するには、まず`capabilities`から開始します。登録されたサンプラーコードは読み込まれたサウンドフォントではありません：作曲が要求されたGMプリセットを読み込めない場合、セッションは組み込み楽器を代用し、その代用を報告します。レンダリングされたテイクがないシンガーは一時的なガイドボーカルを再生します。プレビューとエクスポートでは、欠落している楽器、ガイドボーカル、古いテイクが報告され、`sing`は実際のボーカルを生成または更新します。

音声検出は、デスクトップブラウザと同じ標準ディレクトリと追加の`voice_paths`を使用します。検出は、検証または読み込みを行わずに候補ファイルリストを表示します。プロジェクトを含む`capabilities`は、読み込み時に選択された音声メタデータとスピーカー名も報告します。再生可能なプレビューは音声の概要であり、言語モデルがそれを再生するにはオーディオ入力サポートが必要です。再生可能なファイルを納品し、楽譜の検査と音声の測定結果を報告してください。これらを自分で聴いた証拠として扱ってはいけません。

<a id="live-agent-system-prompt"></a>
## ライブエージェントシステムプロンプト

標準的なライブプロンプトは、音楽的決定から始まります：モチーフの発展、フレーズの方向性、歌詞の韻律、和声の動き、セクションの対比、アレンジの役割、そして完全なフィナーレです。モデルは要件に合った執筆順序を選択し、アンサンブルを記述したり、生成レシピを使用したりできます。要求された形式を完成させ、その後、繰り返しのローカルな微調整を行い、実際の楽譜とレンダリングされたセクションを確認し、その観察事項を聴き取りの好みとは区別します。

音楽的な知識は`crates/auris-agent/src/prompts/musical-design.md`にまとめ、起動時の曲案作成、歌詞生成、エージェントパネルの標準・実験用プロンプトで共有します。モチーフのリズムと展開、息継ぎ、テンション、サビの音域、歌詞との対応、編曲、間奏、エフェクト、部品ごとの試聴評価を扱います。

起動時はまず3つの方向性を選び、その後、各候補を設定済みのエージェントが独立した空の譜面から制作します。選択した楽器・歌声を引き継ぎ、エージェントパネルと同じ作曲プロンプトで、歌詞、セクションのコード進行、ノート、楽器の交代や必要なSFX、エフェクト・音量バランスを仕上げます。主旋律・対旋律・特徴のあるベースやフィルはノート単位で制作し、自動生成は単純なコード伴奏・アルペジオ・基本のドラムに限ります。

ノート編集、ミキサーの確認、現在の譜面に対応した歌声、最終編集後の全曲の音声計測を確認してから、試聴・採用用の候補を保持します。不足は最大2回追加制作を求め、失敗時はエラーを表示します。従来の自動作曲に置き換えることはありません。候補ごとのエージェント処理は20分を上限とし、キャンセルと明示的な権限拒否を尊重します。新しい候補内のノート置換は許可しますが、対話的な承認が必要な操作は実行しません。外部評価モデルやシェルの準備は不要です。これらは制作工程の確認であり、音楽的な良さの証明ではありません。歌詞生成では言葉とフレーズの構成に適用し、未作成の旋律の音高を前提にしません。

ライブ編集の指示は`crates/auris-agent/src/prompts/composition.md`にあります。標準プロファイルには操作規約の`prompts/live-tools.md`も含まれます。歌ものの構成、フレージング、演奏の共有ガイドは`default_system_prompt`で追加されます。CodexとClaude Codeは、同じ解決済みの作曲プロンプトを受け取ります。

設定 → エージェントには、Codex、Claude Code、Rigモデルが共有する複数行の**システムプロンプト**エディタが含まれています。現在の標準プロンプトがすべて入力されます。編集すると一般的なプロンプトが置き換えられ、標準テキストに追加されるわけではありません。Enterキーは改行符を挿入し、プラットフォームのControl/Command+Enterショートカットで設定が適用されます。このエディタは、選択を移動せずに日本語入力、クリップボード操作、ホイールスクロールをサポートしています。

**適用**はプロンプトをアプリケーションのエージェント設定に保存し、次のリクエストから使用します。実行中のリクエストは元の設定で終了します。適用せずに設定を閉じると、保存されたプロンプトは変更されません。**標準プロンプトを復元**はドラフトを復元し、将来のアップデートを含む組み込みのデフォルトを適用して再開します。空のプロンプトもこれらのデフォルトを選択します。保存に失敗した場合はドラフトは保持され、有効な設定は変更されません。

これにより、ライブエージェントの共有指示が編集されます。ネイティブのCLIツールガイド、操作スキーマ/ヘルプ、オプションのワークフローレスポンス、権限チェックはそれぞれ別々に保持されます。承認レビューおよびオーディオ批評指示は独立しています。保存ファイルMCPは独自の指示を使用します。カスタムプロンプトは、標準プロンプトと同様にローカルモデルのコンテキスト予算にカウントされます。

<a id="ollama-configuration-and-failure-recovery"></a>
## Ollamaの構成と障害復旧

設定 → エージェントはコンテキストサイズ（32K、64K、128K、256K）と思考（モデルデフォルト、オフ、オン）を共有設定に保存して公開します。出力トークン制限は、各応答ごとに4K、8K、16K、32K、または64Kを選択し、次のリクエストに適用されます。出力量を増やすと、入力スペースを確保するために必要に応じてコンテキストウィンドウも拡大し、コンテキストを減らすと出力制限が下がる可能性があります。デフォルトのリクエストは`options.num_ctx=32768`を設定し、各完了を`options.num_predict=4096`にデフォルトし、再現可能なツール引数をモデルのチャットサンプリングプリセットを継承するのではなく温度0を使用します。これらはリクエスト設定であり、インストール済みのモデルやOllamaサーバー構成を変更するものではありません。リクエストされたコンテキストはOllamaのサーバーデフォルトとは独立しています。16384未満の値は拒否されます。ツールカタログだけでかなりのコンテキストが必要だからです。モデルディスカバリーはリクエストされたコンテキストをアーキテクチャの最大値とは別に報告します。プリフライトチェックはツールサポートを確認し、報告されたモデルの最大値を超えるリクエストを拒否します。

各モデル呼び出しの前に、コンテキストガードはツール、プレアンブル、履歴、出力用の予約領域の4096トークンを割り当てます。応答が入力トークン数を報告した後、変更されていないリクエストプレフィックスは、測定された数に新たに追加されたメッセージの推定値を加算します。推定値はメッセージ内容を直接カウントし、JSONの輸送エスケープを再度カウントせず、非ASCIIテキストのために余分な余裕を確保します。最初の呼び出し、変更または短縮された履歴、利用不可の使用数、そして非透明なメディアの使用は、保守的な構造推定値を使用します。これらのフォールバックカウントはトークナイザーの測定値ではありません。

新しいリクエストを行う前に、スペースを確保するために、古い完了した会話のやり取りを一緒に削除できます。現在のリクエストとその進行中のツール呼び出しと結果はそのまま残ります。残りの予算がウィンドウを超えると、エージェントはコンテキストを増やすか新しい会話を開始する指示とともに停止します。OpenAI対応プロバイダーは独自のコンテキストポリシーを維持しており、Ollama固有のパラメータを受け取っていません。生成制限で停止されたOllamaの応答は、テキストや文法的に有効なツール呼び出しが含まれていても未完了の応答です。エージェントはこれらの呼び出しを実行する前にその制限を報告します。前のライブ編集は、より小さなフォローアップリクエストのために利用可能です。

パネルのコンテキストゲージは、すべてのツールループステップの入力を追加するのではなく、最後のモデルリクエストからの入力トークンを使用します。JSON回答では、このカウントは`input_tokens`として表示され、実行の集計値は`total_input_tokens`として別途利用可能です。

プロバイダーからの進捗がない5分が経過すると、モデルリクエストは停止状態になります。ツール処理は完了させても構いませんが、アクティブなマルチステップコンポジションは合計で5分を超えても問題ありません。同じツール引数の2回の失敗により3回目の実行が停止します。引数を変更することで修正が可能です。成功した呼び出しは、その署名の失敗回数をクリアします。中断されたJSON会話はリクエストと中断概要を保持するため、次のやり取りで現在のドキュメントを確認して再開できます。完了したライブ編集はセッションに残ります。


<a id="agent-permissions-and-context-compaction"></a>
## エージェントの権限とコンテキスト圧縮

エージェントパネルには、[Picocode](https://github.com/uthree/picocode)の許可モデルに従って、5つの永続モードがあります。

| モード | 行動 |
| --- | --- |
| 読み取り専用 | 読み取りのみを行い、許可ルールがあっても文書変更を拒否し、インターネット検索の承認を求めます。 |
| 編集 | 通常のライブ編集を適用し、削除、配置の変更、インターネット検索を確認します。 |
| 計画 | 検査して計画を提案します。許可ルールがあっても文書変更を拒否します。 |
| 自動レビュー | 通常のライブ編集を適用します。Editモードで確認が必要な独立したモデルレビュー操作があります。 |
| バイパス | 拒否ルールを適用し続ける間、確認をスキップします。 |

拒否ルールはすべてのモードで許可ルールに優先します。読み取り専用モードでは、許可リストに登録されていても文書変更を拒否します。権限セクションには、各正確な操作に対してデフォルト、許可、拒否の選択肢があります。`edit_project.*`および`*`行は、デフォルトと拒否の間のみ切り替えられ、意図的な広範な許可は`/allow`コマンドで引き続き利用可能です。承認はプロジェクト、操作、正確な引数を表示します。一度許可された操作は、現在の文書改訂時のそのコマンドにのみ適用され、承認を待っている間に行われた編集はそれを無効にします。常に許可は操作ルールを保存します。操作を拒否すると、モデルに拒否が返されます。モードまたはルールを変更すると、保留中の承認がキャンセルされます。エージェントを停止すると、その保留中の作業がキャンセルされます。

新しい会話を開始すると、アクティブな作業を停止し、表示されているトランスクリプトをクリアし、保存された会話履歴を削除する前に、明示的な確認が必要です。確認をキャンセルすると、会話とアクティブな作業は変更されません。

モードボタンまたは`/mode read_only|edit|plan|auto_review|bypass`を使用してください。Shift+Tabは3つの通常のモードを切り替えます。バイパスするには明示的な選択が必要です。承認が保留中の間は、Shift+Tabはモードを変更せずに承認を拒否します。`/permissions`はルールを開き、`/allow OPERATION`、`/deny OPERATION`、`/default OPERATION`はそれらを編集します。確認が保留中の間は、Escapeは拒否し、Ctrl+Enter（macOSではCommand+Enter）は一度だけ許可し、Shiftを追加すると常に許可されます。

これらのモードは、すべてのバックエンドのライブツールを制御します。Rigはライブドキュメントカタログを公開します。CodexとClaude Codeもネイティブシェルとファイルツールを公開します。ネイティブ承認は、Permissionsで`cli_command`、`cli_file_change`、および（Claudeの場合）`cli_file_read`として表示されます。ファイル変更やコマンドは、正確なルールまたは広範なルールで許可されていない限り、Editモードで確認が必要です。読み取り専用とPlanは、許可リストに登録されている場合でも、ネイティブコマンドやファイル変更承認を拒否します。ネイティブのファイル変更やコマンド効果はAuris Undoの範囲外です。ウィンドウの裏側で`.auris`ファイルを書き直すのではなく、ライブツールを使用して開いている曲を編集してください。

CLIツールは保存されたプロジェクトのフォルダから開始されます。保存されていない曲は、会話が終了すると削除される一時的なスクラッチスペースを使用します。成果物に対して明示的な永続的な目的を指定してください。Codexは読み取り専用のサンドボックスと非信頼コマンド承認ポリシーを保持しているため、信頼できるサンドボックスからの読み取りは確認プロンプトが表示されません。書き込みやエスカレートされたコマンドはパネルの承認ゲートを経ります。ClaudeはBash、Read、Glob、Grep、Write、Edit、NotebookEditを公開し、askルールを使用してネイティブ呼び出しをパネルを通じてルーティングします。関係のないMCPサーバー、プラグイン、フックは分離されたままです。スタンドアロンMCPは保存されたファイルツールを保持し、パネルのポリシーは適用されません。

**Auto review**を選択するか、`/mode auto_review`を入力して、モデルにあなたの代わりに承認してもらうことができます。レビューアは、選択したバックエンドとモデルをツールなしで別々の会話で使用します。人間のリクエスト、正確な論拠、コマンドテキスト、利用可能なファイル差分を評価します。明確でリスクが低い作業は一度限りの承認を受けられますが、明確な拒否は操作をブロックします。不確実な決定、タイムアウト、利用できないモデル、過大な入力、無効な応答は手動確認に戻ります。トランスクリプトには決定と理由が表示されます。レビューが進行している間に手動で承認または拒否できますが、そうすると保留中のレビューがキャンセルされます。変更されたドキュメントは変異承認が無効になり、遅延した結果は別のリクエストを承認できません。レビューは決して「常に許可」ルールを作成せず、拒否ルールを覆すこともありません。各レビューごとにモデルリクエストを追加しますが、これはオペレーティングシステムサンドボックスではなく、誤解の可能性のある推奨事項です。バイパスは、人間による確認と自動レビューの両方をスキップし続けます。

レビュアーは、制限された現在のプロジェクトスクリプトのスナップショットと、最近完了したネイティブ呼び出しも受け取ります。長くて繰り返されるコマンドテキストは、内容を失わずにエンコードされます。[自動承認証拠](agent-review-evidence.ja.md)で、収集制限、完全性チェック、残りのファイル変更レース境界を確認してください。

コンパクトコンテキストまたは`/compact`は、構成されたモデルとの以前のやり取りを要約しますが、そのモデルのツールは付与しません。最新の2回の完了したやり取りはそのまま保持されます。要約には、目標、制約、決定、識別子、進捗、失敗、未完了の作業が含まれます。会話履歴とともに保存され、その会話が再開されるときに復元されます。空の、サイズが大きすぎる、または失敗した要約は元の履歴をそのまま残します。要約リクエストに収まらない非常に大きなやり取りもそのまま残ります。

自動圧縮は、選択した推定履歴閾値（70％または85％；デフォルトは85％）でのリクエスト間または、16回の完了した取引後に行われます。Permissionsで無効にすることができます。カウントは推定値であり、トークナイザーの測定値ではありません。既存のリクエスト別コンテキストガードは最終的な予算チェックとして残ります。圧縮はツール操作の途中や承認リクエストの途中には決して実行されません。
