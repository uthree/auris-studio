# 歌詞分析・診断・局所修復

[English](lyric-harness.md)

歌詞ハーネスは、作曲または編集の前に構造的な適合を確認します。歌声モデル、推論サーバー、オーディオデバイス、読み取り中のドキュメント変更は必要ありません。芸術的な品質を評価したり、変更後のフレーズが意味を保つことを証明したりはしません。

<a id="establish-a-reading"></a>
## 読みを確定する

`analyze_lyrics` は元の日本語 `text` と任意の `readings` を受け取ります。

```json
{
  "text": "ずっと君と、珈琲",
  "readings": [{"phrase": 2, "kana": "コーヒー"}]
}
```

音楽フレーズは、改行または日本語の句読点（`、。！？!?`）で区切った空でない部分です。フレーズ番号と行番号は1から始まります。`start_char` と `end_char` は元のテキストにおけるUnicodeスカラーの0始まりオフセットで、終端は排他的です。漢字とモーラの推定対応ではなく、フレーズ全体を示します。

各フレーズには、原文、読み、読みの出典、モーラ表記、IPA音素、語尾・鼻音・長音記号のフラグが含まれます。長音記号フラグは明示的な `ー` を示すもので、他の母音列が短いという推測ではありません。辞書がインストールされていればフレーズ全体を読み、なければ仮名表を使います。読めないフレーズはテキストとエラーを保持し、`complete` をfalseにします。読みの上書きは仮名だけで、既存の1フレーズに対するそのリクエストだけに有効です。後続の作曲の発音は変更しません。

仮名では長いオを「おう」、長いエを「えい」と書きます（りょうて、せんせい）。仮名表は書いたとおりに歌います。辞書がインストールされていて、元のテキストを読みと同じ数のモーラに読み、違いが「その母音の後のう・い」だけの場合は、辞書の長音で歌い、表記は読みのまま残します。たとえば両手に読み「りょうて」を付けると、*ryo-o-te* と歌います。それ以外の違いがあれば意図した別の読みとみなし、書いたとおりに歌います。辞書がないときは、長音を「ー」で書いてください（りょーて）。`write_lyrics` の `reading` も同じように読みます。

<a id="fit-a-phrase-to-its-notes"></a>
## フレーズを音符数に合わせる

モーラは言葉の単位で、メロディーの単位ではありません。各モーラの `slot` は、そのモーラが音符に何を求めるかを示します。

- `note` は音符を1つ使います。`ん` もこれです。
- `hold` は伸ばす長音です。`ー` と、語の中で直前と同じ母音が続くもの（`さあ` の `あ`）が当たります。音符を1つ使うことも、前の音符の終わりとして歌うこともできます。
- `rest` は `っ` です。音符を使わず、前の音符の後の休符になります。

したがって、フレーズは `min_notes`（長音をすべて前の音符にまとめた数）から `max_notes`（長音にもすべて音符を割り当てた数）までの音符数で歌えます。辞書は東京をトーキョーと読むので、辞書が読んだ長音は `hold` になります。`ゆこう` のような仮名書きは書いたとおりに読むので、まとめたいときは読みに `ゆこー` と書きます。

`fit` には、各フレーズを歌う音符数（繰り返すモチーフの音符数など）を渡します。

```json
{
  "text": "さあ いっしょに ゆこー",
  "fit": [{"phrase": 1, "notes": 6}]
}
```

`fit` を渡したフレーズには `fit.verdict`（収まる `fits`、字余りの `too_many_moras`、字足らずの `too_few_moras`）と、削る（正）または足す（負）モーラ数の `fit.excess` が付きます。収めるために勝手にまとめたり分けたりはしません。`note_reading` は読みを `|` で音符ごとに区切ったものです。収まるときは指定した音符数、収まらないときは `max_notes` の区切りになります。長音をまとめる必要があるときは、フレーズの終わりに近いものからまとめます。

`note_reading` は `write_lyrics` の `reading` にそのまま渡せます。`|` を含まない読みは、これまでどおり1音符に1モーラです。区切った読みで前のモーラと同じ音符に置けるのは、伸ばす長音と末尾の `っ` だけで、それ以外は拒否します。`っ` で終わる音符は閉鎖の音素を歌わないので、次の音符はその音符の終わりから32分音符（120 tick）以上後に始まる必要があります。

<a id="diagnose-a-composition-or-existing-phrases"></a>
## 作曲または既存フレーズを診断する

`check_spec` は構文と設定を確認します。次に、完全な `.asong` TOML文書を含む `spec` で `diagnose_song` を呼びます。共有歌詞は `melody_from` が共有メロディーを宣言した箇所だけ比較します。診断はセクション全体のモーラ数ではなく、各音楽フレーズを確認します。後続の歌詞を空にすると、そのセクションは意図的に器楽になります。

結果には原文順の分析と、安定した `code`、`severity`、セクション／フレーズの位置、参照値、期待値と実際の値、修復範囲を持つ独立した問題が含まれます。`status` は `pass`、`fail`、`incomplete` です。既知の違反は不完全入力より優先されますが、`complete` はすべての検査を実行できたかを別に記録します。読めないフレーズは依存する比較を止めますが、他の読めるフレーズのエラーは隠しません。作曲でもドキュメントを置き換える前に同じ診断を使います。

既存プロジェクトでは、`read_notes` が返す正確な歌唱クリップIDと保存ノートの0始まりインデックスを使います。

```json
{
  "comparisons": [{
    "reference": {"clip": 10, "notes": [0, 1, 2, 3, 4, 5]},
    "target": {"clip": 11, "notes": [0, 1, 2, 3, 4, 5]}
  }]
}
```

`spec` または空でない `comparisons` のどちらか一方だけを渡します。ライブ比較は保存音素を読み、モーラ／語尾位置だけでなくピッチ、相対オンセット、長さ、装飾も検証します。選択インデックスは連続した重複しないフレーズを構成する必要があります。保存音素が各ノートに1モーラを確立している場合は、`write_lyrics` と同様に `+` が続く元のフレーズラベルを使用できます。空歌詞や欠落・複数モーラ音素は不完全として報告されます。すべての診断は現在のドキュメントリビジョンを返します。

保存ファイルツールはプロジェクトIDまたはパスを `project` に追加します。`analyze_lyrics` と仕様ベースの `diagnose_song` では任意なので、下書き確認だけのためにプロジェクトを作る必要はありません。ライブツールは開いているドキュメントを使い、`project` を省略します。大きな結果には既存の不変 `read_report` ページを使うため、返されたレポートIDとJSONポインターを保持してください。

<a id="preview-and-apply-a-local-repair"></a>
## 局所修復をプレビューして適用する

1回の修復ラウンドでは対象、比較参照、必須キーワードを固定します。`repair_lyrics` は1〜3個の候補を受け取り、編集前にすべてを検査します。

```json
{
  "target": {"clip": 11, "notes": [0, 1, 2, 3, 4, 5]},
  "reference": {"clip": 10, "notes": [0, 1, 2, 3, 4, 5]},
  "expected_revision": "COPY_FROM_READ_NOTES_OR_DIAGNOSIS",
  "candidates": [
    {"text": "きみとあえる"},
    {"text": "きっとあえる"}
  ],
  "required_keywords": ["あえる"],
  "apply": false
}
```

参照が `ずっときみと` を歌う場合、2番目の候補は6モーラと2番目の語尾に一致します。応答は最初に合格した候補を1始まりの `selected_candidate` で選び、全候補の診断を保持します。候補は完全な音楽フレーズでなければなりません。キーワードは原文テキストの文字列として確認します。任意の候補 `reading` は実際に適用する仮名を指定します。

候補の意味を確認し、同じリビジョンで選択候補を `apply: true` にして再送します。`reference` を省略すると、対象の既存の語尾パターンを保持します。参照と対象は音楽スロットが一致し、重なってはいけません。古いリビジョン、無効な選択、利用できないテンプレートではドキュメントを変更しません。合格候補がなければ `applied` はfalseで、すべての候補診断が残ります。

適用は選択した対象ノートにだけ歌詞とモーラ音素を書き、語または発音が変わった箇所だけ長さピンを解除します。ピッチ、タイミング、ベロシティ、装飾、その他のノートは保持します。Undo 1回で編集を戻せ、プレビューと無操作の適用は履歴を増やしません。仮名だけの候補はモーラごとのノートラベルを使います。仮名以外のテキストや明示的な読みのある候補は、最初のノートに原文を置き、残りに `+` を付けます。これは `write_lyrics` と同じ扱いです。保存後も各ノートは固有の発音を保持します。

ライブエージェントは、ツール呼び出しや転送をまたぐ1回のユーザー入力に対して、対象／リビジョンごとに異なる候補を最大3個に制限します。プレビュー済み候補を適用しても別の候補として数えません。ラウンド中に参照やキーワードを変えること、同じプレビューや適用を繰り返すことは拒否されます。保存ファイルの単独呼び出しにも同じ3候補上限があり、呼び出し元はラウンドを保持して無限バッチを止める必要があります。

適用後はノートを読み戻し、関連フレーズをすべて診断して意味の保持を確認します。歌唱状態を検査し、古いテイクは `sing` で再レンダーします。構造検査だけで歌唱完成を主張しないでください。3候補が失敗したら、残る診断と、変更が必要な歌詞または音楽上の制約を報告します。
